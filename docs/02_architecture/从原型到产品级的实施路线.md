# 产品化改造方案：从原型到产品级（可行性确认书）

本文是「原型级 → 产品级」的改造评估与路线提案。**本文件是确认书**：文中标注 ★ 的决策项需你拍板后才能进入实施，其余部分为可执行结论。未做任何代码改动。

## 0. 一句话结论

原型到产品级不是"把页面和功能补齐"，而是**把权威从浏览器搬到服务端**，并同时补上四道门禁：真实数据、真实账本、真实联机、真实运维。路径上应按**纵向闭环**推进（每阶段打通一条真实业务链并过门禁），而不是按层铺开（先补完数据库再补前端）。

## 1. 产品级的判定口径（6 条 DoD）

| # | 目标 | 可度量口径 |
| --- | --- | --- |
| D1 | 服务端唯一权威 | 账号、资产、牌局结果、返佣的判定 100% 在服务端；浏览器直改 IndexedDB 无法改变任何余额或牌局结果；浏览器伪后端目录可删除后功能不降级 |
| D2 | 资产正确性可审计 | 账本分录平衡（属性测试覆盖每种流水）；系统账户与玩家账户守恒边界成立；幂等键保证重复提交只生效一次；赠币流水门槛、冻结期、返佣 10/8/5/3 与文档口径逐条对齐 |
| D3 | 契约即真相 | OpenAPI 由 `packages/contracts` 的 schema 生成；前后端类型由同一来源产出；契约测试进 CI，破坏性变更在合并前被发现 |
| D4 | 真实联机 | 房间、发牌、摆牌、结算由服务端权威判定；支持断线重连、超时托管、防重复提交；多客户端同房间结算结果一致 |
| D5 | 可运维 | CI 全绿、生产镜像、数据库迁移（可升级/可回滚）、备份恢复演练、指标与告警、灰度与回滚预案、日志按 requestId 可追溯 |
| D6 | 可维护与可理解 | 模块边界清晰、错误类型化、样式有 token、关键路径有测试、玩家文案可抽取、资金规则在代码里有注释与文档出处 |

## 2. 现状与目标差距矩阵

| 能力域 | 目标 | 现状（实测） | 差距 | 阶段 |
| --- | --- | --- | --- | --- |
| 服务端运行时 | Koa + MySQL + Redis + Socket 权威 | Koa **6 个只读路由**，无 DB、无 Redis、无 Socket.IO | 几乎全部 | P0 |
| 数据层 | Sequelize + 迁移 + 表约束（id/status/三时间/注释） | **0 张表、0 个迁移、0 个模型**，代码里没有任何 sequelize/mysql2 依赖 | 全部 | P0 |
| 身份与会话 | 服务端签发 JWT、设备会话、服务端撤销 | 浏览器**自签 ES256**，私钥存 IndexedDB，校验也在浏览器 | 全部 | P1 |
| 资产与账本 | 双账本 + 系统账户 + 流水门槛 | 规则已在浏览器 IndexedDB 内实现（口径大体正确，但**无权威性**） | 迁移 + 补齐 | P1 |
| 十三张 | 服务端权威结算 | 纯本地练习，前端本地判定牌型 | 全部 | P2 |
| 支付 | 渠道回调 + 验签 + 对账 + 冻结 | 仅模拟支付接口 | 全部 | P3 |
| 返佣 | 五级 10/8/5/3 + 冻结期 + 快照 | 浏览器内实现，且返佣列表当前返回空 | 补齐 | P3 |
| 前端生产态 | 生产构建功能等价于开发态 | 生产构建**只注入 gameExperienceApi**，钱包/社交/客服/邀请全部消失 | 全部 | P0-P1 |
| 运营后台 | 真实数据 + 权限 + 审计 | 19 个领域 92 个文件全是本地演示数据；登录页输入框为 disabled，无鉴权 | 全部 | P4 |
| 工程基线 | CI / 测试 / lint / 镜像 / 迁移 | 审计时无 CI、无 lint、无格式化、无钩子、无生产镜像；作者已于审计期间提交 `78face0`（340 文件），提交历史问题解除，但自动化关卡当时仍缺 | 自动化关卡全部 | P0 |
| 可观测 | 指标、日志、告警 | 只有响应体里的 `requestId` 字段，无指标无告警 | 全部 | P0 起 |
| 合规与留存 | 密钥管理、审计留存、数据留存期 | 素材侧已分离；业务侧未定义（客服文件 2 年、审计不可改写等仅在文档） | 部分 | P4 |

**读法**：资产规则与 UI 的"完成度"远高于"可上线性"。二者差距集中在**权威位置**与**自动化关卡**两处，这两处不补，后面接再多的页面也不会变成产品。

## 3. ★ 需要你拍板的架构决策

| # | 决策 | 方案 A（建议） | 方案 B | 代价与影响 |
| --- | --- | --- | --- | --- |
| A | 领域规则的代码归属 | 把 `apps/web/src/platform/browser-api/**` 里的**领域规则**下沉到 `packages/domain`，浏览器端与服务端共用；浏览器端只留 IndexedDB 适配器与桩 | 在服务端重写一遍领域规则 | A 需一次拆分重构（1~2 周）并用端口接口隔离浏览器差异，但避免两套实现漂移；B 初期快、后期必然不一致，**不推荐** |
| B | 浏览器伪后端下线方式 | 契约对齐后**按端点分批切换**（feature flag 双轨），最后整体删除 `browser-api/` 目录 | 一次性切换 | 一次性切换风险集中在一天；分批可回滚但需短期维护双轨 |
| C | 实时通信与房间权威 | Socket.IO + **独立房间 worker 进程**持锁，服务端判定牌局结果 | 单进程内置房间 | 多进程需要房间路由与粘性策略，单进程在长局与断线场景有串行瓶颈 |
| D | 数据层与迁移工具 | Sequelize + umzug（或 sequelize-cli），表结构严格按 `docs/05_data` 规范落地 | Sequelize + 自写迁移 | 迁移工具影响回滚能力，需与 D5 门禁绑定 |
| E | 运行时与依赖版本 | MySQL **9.7 已是 LTS**（官方 EOL 公告已把 8.4 LTS 与 9.7 LTS 并列为推荐），可继续锁定；Redis 8 为 RSALv2/SSPLv1/**AGPLv3** 三许可，若担心 AGPL 对网络服务的源码义务可换 **Valkey 9.x（BSD-3）**；Node 24 LTS 可用 | 降级 8.4 LTS / 换 Valkey | 换 Valkey 需改连接串与运维手册，但消除许可证不确定性 |
| F | 五端封装方案 | 先 Web + PWA，App 封装在 P2 之后再定（Capacitor / Tauri / 原生壳） | 现在就锁定 | 现在锁定会反过来约束 UI 基建与素材规格 |
| G | i18n 落地时机 | P2 之前把**玩家可见文案**抽到 `locales/zh-CN`，后台与调试文案可缓 | 全量一次性抽取 | 全量抽取成本高、收益低，且会与 UI 改版同时发生 |

## 4. 阶段路线（每阶段一个纵向闭环 + 门禁）

### P0 地基（约 2 周）
- **交付**：仓库基线（提交历史已由作者整理为 `78face0`）；CI（typecheck/test/build）；ESLint+Prettier+钩子；真后端骨架（Koa + 错误码/日志/健康检查）；Sequelize + 迁移框架 + 首批表（user、资产账户、账本分录、系统账户）；契约生成 OpenAPI；生产镜像与 compose profile 分离；结构化日志 + requestId 贯通 + `/health` `/ready`；伪后端规则下沉到 `packages/domain`（决策 A）。
- **门禁**：CI 绿；迁移可升可降；容器起停与**备份恢复演练**通过；OpenAPI 与 schema 同源；生产前端构建与开发态能力对齐。

### P1 身份与账本（约 3 周）
- **交付**：user 表与角色；注册/登录/设备会话/刷新与服务端撤销（JWT 由服务端签发）；资产账户（金币/余额双账本）与分录写入；赠币与流水门槛；系统账户记账与守恒边界；前端登录态接真实服务端。
- **门禁**：账本平衡**属性测试**（随机流水序列下总和恒等）；并发与重复提交幂等测试；浏览器篡改本地数据不影响任何余额；越权用例（他人 userId / 越权代操作）全部拒绝。

### P2 十三张联机闭环（约 3 周）
- **交付**：房间与牌局由服务端权威持有（决策 C）；发牌/摆牌/开牌/结算全部服务端判定；断线重连与超时托管；结算写账本；前端牌桌改为服务端权威 + 事件驱动；牌局复盘可对账。
- **门禁**：多客户端同房间结算一致；重放/重复提交防护；断线重连后状态一致；牌局结果与账本分录一一对应可查。

### P3 资金闭环（约 3 周）
- **交付**：充值（受控模拟→真实渠道，验签与幂等回调）；兑换与提现审核；返佣五级 10/8/5/3 与冻结期（充值 2 天/客损 1 天）、结算快照；对账任务与差异告警；系统账户与渠道费分录。
- **门禁**：资金对账日报无未解释差异；提现审核幂等；返佣金额逐级抽检与规则一致；提现身份三选一与最低 1000 枚整数倍门槛生效。

### P4 运营后台与上线（约 3 周）
- **交付**：后台接真实 API（19 个领域按落地顺序裁剪，删除演示数据适配器）；管理员登录、权限矩阵与不可改写审计；监控看板与告警；压测；灰度与回滚预案；数据留存与合规核对。
- **门禁**：压测达标（并发房间数、结算延迟、账本写入吞吐）；告警可触发可恢复；回滚演练通过；审计可追溯敏感操作。

> 时间为量级参考，取决于决策 A/B 的拆分成本与联调节奏。

## 5. 每阶段必须过的横向质量门禁

1. 类型：全仓 `vue-tsc`/`tsc` 通过，契约包独立检查。
2. 测试：单元 + 契约 + 端到端；资产不变量属性测试；关键路径回归清单。
3. 资产专项：每新增一种流水类型，必须同时补账本平衡断言与对账口径。
4. 性能：基线（首屏、包体、房间数、结算延迟）纳入 CI 报告或看板。
5. 安全：依赖审计、密钥只留服务端、越权与注入用例、限流与风控基线。
6. 文档：受影响的 SDD 与每个 Markdown 的「变更历史」同步更新（AGENTS.md 约束）。
7. UI 几何：凡改动页面或样式，按 `docs/06_ux/大厅与后台UI走查与优化建议.md` 的口径复验桌面/移动视口。

## 6. 明确"不要做"

- 产品化阶段**不再扩页面**：43 份设计文档已足够，先补真实现（UI 审计里的 P0/P1 缺陷在 P0 阶段修即可）。
- 服务端权威落地前，**不要**接真实支付通道、真实返佣发放、真实提现出款。
- **不要**把 browser-api 的规则复制一份到服务端——必须下沉共享，否则两套实现必然漂移。
- 同一批次只做一件事：不要同时改 UI 与账本，否则问题无法归因。
- 不要用"前端能跑通"作为阶段完成标志，门禁以服务端可验证为准。

## 7. 产品级最小内核（首个可验收纵向闭环）

> 玩家注册 → 设备登录 → 进入十三张新手厅 → 服务端发牌 → 摆牌 → 服务端结算 → 金币记账 → 端上余额可见 → 后台可见该局与分录 → 断线重连后状态一致

这条链打通并通过 P2 门禁，项目即从"原型"变为"产品级最小内核"；其余功能（社交、金币集市、客服、活动、代理）按同一模板复制，不再产生新的架构风险。

## 8. 未闭环事项

- 未做容量估算（目标房间数、并发连接、结算 TPS、账本写入量），影响 P2/P4 硬件与压测口径。
- 未做第三方支付渠道选型、费率与合规评估（USDT/TRON 自建通道也未做链上对账设计）。
- 未做五端封装方案的对比与选型（决策 F）。
- 未评估真实数据量下账本属性测试的运行成本与抽样策略。
- 未定义安全渗透测试范围与合规基线（数据留存、审计留存、未成年人/地区限制等）。
- 未复核各第三方服务（短信、邮件、Kling、OpenAI）在生产环境的 SLA 与降级策略。
