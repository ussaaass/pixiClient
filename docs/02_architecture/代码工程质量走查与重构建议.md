# 代码工程质量走查与重构建议

本文记录 2026-10-21 对仓库代码的工程化审计：按**工程化、整洁、结构化、可读性、可理解性**五个维度给出量化结论与重构建议。数据来自实际扫描与实测（`vue-tsc`、依赖图、样式统计、注释统计、引用关系扫描），不改代码。

## 审计范围

- 代码规模：`apps` / `packages` / `games` / `tools` 下 TS + Vue + CSS 共 **39,680 行**；其中 `apps/web` 与 `apps/admin` 是主体，`packages/contracts` 26 个模块是共享契约源。
- 验证方式：`vue-tsc --noEmit` 实测通过（1m43s）；依赖与引用关系用脚本扫描；样式、注释、断点、断言等用量化统计。
- 判定口径：凡"没有工具保证"一律记为缺失，不因当前看起来干净而放过；凡只能靠人眼维持的约定，记为结构风险。

## 一、工程化：工具链能保证的事情太少

| 维度 | 现状 | 证据 |
| --- | --- | --- |
| 持续集成 | 无 | 仓库无 `.github/`、无其他 CI 配置 |
| Lint / Format | 无 | 无 ESLint、Prettier、EditorConfig、lint-staged、husky |
| Git 历史 | 近乎不可用 | 审计时全仓仅 1 个提交（`1a4bcc1 chore: initialize gameing hall project`）+ **176 个未提交改动**（5912 增 / 850 删）。审计期间已由作者提交为 `78face0 feat: complete player and admin platform workflows`（340 文件，+12619 / −850），基线问题已解除 |
| 包管理器 | 双轨 | 主工程 pnpm workspace；`tools/asset-generation` 是独立 npm 工程（自带 `package-lock.json` 与 `node_modules`，`undici` 装了两份），且 `tools/` 不在 `pnpm-workspace.yaml` 内 |
| 共享契约包 | 零独立检查 | `packages/contracts` 与 `packages/admin-contracts` **既无 `tsconfig.json` 也无 scripts**，没有 typecheck 也没有 test；只有被消费时才被顺带检查 |
| 十三张客户端 | 无测试 | `games/shisanshui/client`（Pixi 牌桌 829 行）只有 typecheck/build，没有 test 脚本 |
| 编译严格度 | 中等 | `tsconfig.base.json` 开了 `strict`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`，但未开 `noUnusedLocals` / `noUnusedParameters` / `noImplicitOverride` / `noFallthroughCasesInSwitch` |
| 构建产物 | 不存在 | `apps/server` 没有 build 脚本；唯一镜像 `Dockerfile.dev` 跑 `tsx watch`，compose 的 `full` profile 起的也是开发进程，**没有生产镜像与部署路径** |
| 类型反馈速度 | 慢 | web 全量类型检查 1m43s，无 `tsBuildInfo` 增量缓存，每次全量重算 |

**判断**：项目的"工程化"目前只依赖 TypeScript 严格模式与作者自律，没有任何一个自动化关卡（CI、lint、格式化、提交钩子）能在代码变坏时拦住。176 个未提交改动叠加在单个初始提交之上，等于**没有任何可回滚的工程基线**——这是当前最高优先级的工程风险，与 UI 问题无关。

> **整改状态（2026-10-21，第一批已落地）**：上表所列的"无 CI / 无 Lint / 无 Format / 无钩子 / 契约包零检查"五项均已补齐，实测通过：
>
> | 项 | 落地物 | 实测结果 |
> | --- | --- | --- |
> | CI | `.github/workflows/ci.yml`（pnpm 12.10.1 + node 24.21.0） | lint → format:check → typecheck → test → build 五关串行 |
> | Lint | `eslint.config.js`（flat config，ESLint 10 + typescript-eslint 8 + eslint-plugin-vue 10） | `pnpm lint`（packages/games/apps/server）**0 error / 0 warning** |
> | Format | `.prettierrc.json` + `.prettierignore` + `.editorconfig` | `pnpm format:check`（packages/games）**全部通过**（39 个文件已按 140 列 / 单引号 / 尾逗号落盘） |
> | 钩子 | `.husky/pre-commit` → `lint-staged`（eslint --fix + prettier --write） | 已安装，`prepare` 脚本 `husky \|\| true` 保证 CI 安装不失败 |
> | 契约检查 | `packages/contracts` 与 `packages/admin-contracts` 补 `tsconfig.json` + `typecheck` + `test` 脚本 | 契约测试 **7 + 8 = 15 例全绿**；两个包 `tsc --noEmit` 干净 |
>
> **Lint 规则选择说明**：Vue 部分只启用 `flat/essential`（正确性规则），不启用 `recommended/strongly-recommended`。后者包含 `vue/max-attributes-per-line`、`vue/html-indent`、`vue/singleline-html-element-content-newline` 等纯排版规则，在存量模板上会产生 6800+ 条无信息量告警，且与 Prettier 职责重叠。**排版归 Prettier，lint 只负责"对不对"**。
>
> **顺手修掉的真实缺陷**：ESLint `no-useless-escape` 在 `packages/contracts` 中报出 4 处 `\.` 未转义——单引号字符串里的 `\.` 会被静默退化成"任意字符"，使 `CnyAmountSchema`（金额）与 `UtcTimestampSchema`（时间戳）的正则**实际失效**。已改为 `\\.` 并由契约测试锁定回归。
>
> **Compose 卷属主缺陷（本次发现并修复）**：Docker 创建具名卷时属主为 root，而 `dev`/`server`/`web`/`admin` 均以 `user: node` 运行。只要 lockfile 变化需要真正更新 `node_modules`，`pnpm install` 就会以 `ERR_PNPM_PACKAGE_MANAGER_REMOVE_MODULES_DIR / Permission denied` 失败——这正是 README 里那条安装命令在改依赖后跑不通的根因。已新增一次性服务 `prepare-volumes`（`user: root`）把 5 个卷 chown 给 `node`，并让 4 个工作服务以 `condition: service_completed_successfully` 依赖它。实测 `docker compose --profile dev run --rm dev pnpm install --frozen-lockfile` 从失败转为成功（350 包）。

**建议（第一批，低风险）**
1. 先把当前 176 个改动按"大厅 / 后台 / 契约 / 十三张 / 工具链"分 5~6 次提交落地，建立可回滚基线。
2. 引入 ESLint（flat config）+ Prettier + EditorConfig + lint-staged + husky `pre-commit`；规则先只开低争议项（`no-unused-vars`、`no-console`、`vue/multi-word-component-names`、import 顺序）。
3. 建 CI：至少 `typecheck` + `test` + `build` 三条作业，与 README 的 Docker 命令对齐。
4. 给 `packages/contracts`、`packages/admin-contracts` 补 `tsconfig.json` 与 `typecheck`/`test` 脚本；契约 schema 是全系统单一事实源，必须有独立关卡。
5. `tools/asset-generation` 并入 pnpm workspace（`tools/*`），删除其自带 `package-lock.json` 与 `node_modules`。
6. 打开 `noUnusedLocals` / `noUnusedParameters`，先在 `packages/*` 与 `games/*` 试点。

## 二、整洁：一致性靠人眼维持

| 问题 | 证据 | 影响 |
| --- | --- | --- |
| 样式没有设计令牌 | `web/style.css` + `admin/style.css` 共 **2971 处硬编码颜色、1296 个不同色值**，CSS 变量用法仅 25 处 | 换主题、改品牌色需要全量文本替换；同一语义色在不同页面出现几十个近似值 |
| 断点不成体系 | web 用 720/721/760/520/380/438，admin 用 700/980/1000/1050，两套互不引用 | 同一断点概念在两个应用不同值，跨端行为不可预测 |
| 适配器命名三套词 | admin 19 个领域里同时存在 `indexeddb-*`（12 个）、`offline-*`（3 个）、`local-demo-*`（2 个）；`system-config` 一个领域同时留了 `indexeddb-system-config-adapter.ts` 与 `offline-system-config-adapter.ts`，composition 只接了前者 | "假后端"这件事有三种叫法，读者无法从名字判断数据来源与可信度 |
| 目录语义重叠 | `apps/web/src/platform/` 下同时放领域逻辑（`wallet-domain.ts`、`social-domain.ts`）与基础设施（`browser-api/`、`http/`、`preferences/`） | 找"业务规则"和找"传输层"要在同一层翻 |
| 死代码 | `apps/web/src/components/DevelopmentContactCodeInspector.vue` 零引用（脚本扫描全仓，无任何文件 import 它） | 组件仍在构建产物里 |

**建议（第二批）**
1. 建 `packages/theme`（或 `apps/web/src/styles/tokens.css`）：把 1296 个色值收敛成 40~60 个语义 token（surface / brand / state / text 四组），组件只允许引用 token。
2. 统一断点为 `--bp-sm: 720px; --bp-md: 1024px; --bp-lg: 1280px`，web 与 admin 共用一份。
3. 适配器按"数据来源"而非"技术"命名：统一为 `local-persisted-*`（浏览器 IndexedDB 持久化）与 `local-seeded-*`（只读演示数据）两类，删掉 `offline-*`；`system-config` 的双适配器二选一。
4. `platform/` 拆为 `domain/`（纯规则）+ `platform/`（适配器与装配），domain 不允许 import 任何基础设施。

## 三、结构化：模块边界与规模

### 3.1 根组件承担了太多

`apps/web/src/App.vue` **2418 行**，内含 **82 个 `ref`、12 个 `computed`、5 个 `watch`、110 个函数、42 个 import**，同时承载大厅/子厅/社交/消息/钱包/邀请/入口页的全部状态与路由判定。全项目没有 Vue Router（web 靠 `App.vue` 里手写 `window.location.pathname` 正则解析路由），也没有 Pinia 之类的状态容器；admin 反而用了 vue-router——同一产品两种路由模型。

**建议**：`App.vue` 只保留路由与布局，按页面拆成 `lobby/`、`subhall/`、`social/`、`messages/`、`wallet/`、`entry/` 六个页面容器组件，各自持有自己的状态；全局只有会话与公告两块共享状态，用一个轻量 provide/inject 或 Pinia store 承载。

### 3.2 浏览器端伪后端是当前最大的结构债

`apps/web/src/platform/browser-api/dispatcher.ts` **744 行**，承担了钱包、转账、兑换、提现、充值、支付模拟、社交、客服、金币集市、邀请返佣、身份会话等**全部服务端职责**，并以 `BrowserApiServer` 类在浏览器内实现 HTTP 语义。可读性问题集中在：

- 路由表是**一个跨 3 行的数组字面量**（第 119 行，长度 **962 字符**），把约 40 个端点常量用 `...Object.values()` 拼在一起；
- 路由匹配用 **15 个手写正则** + 一串 `??` 三元链（`contactConfirmMatch && ... ? ... : undefined`）；
- 实际分派是 **115 个 `if` 分支**的长链，文件中 **39 行超过 200 字符**，最长达 962 字符；
- `main.ts` 分叉：DEV 走浏览器伪后端并注入全部能力，PROD 只注入 `gameExperienceApi`——**生产构建下钱包、社交、客服、邀请全部消失**，两条启动路径的行为差异没有任何文档说明。

**建议**：
1. 把路由表改成显式声明（`{ method, pattern, handler }` 数组 + 一张匹配表），彻底去掉 if 链与三元链；路由与端点常量同源生成。
2. 明确伪后端只是"契约桩"，把它收敛到 `apps/web/src/platform/browser-api/` 一个目录内，并写清下线条件（真实服务端上线后删除该目录）。
3. 生产启动路径必须与开发路径等价：缺能力时应显式报错而不是静默不注入。

### 3.3 后台领域是同构复制

`apps/admin/src/platform/` 下 19 个领域目录、92 个文件，几乎每个都是 `xxx-application.ts` + `xxx-adapter.ts` + `composition.ts`（+测试）。结构一致是优点，但目前 **19 个领域的业务全部落在本地演示数据或浏览器 IndexedDB 上**，服务端一个后台接口都没有——后台是"能点的空壳"。

**建议**：在真实后台 API 落地前，把这 19 个领域按落地顺序排期，只保留已联调的领域，其余收敛为"接口契约 + 桩"，避免为不存在的后端维护 92 个文件。

### 3.4 契约包的定位正确但没有防线

`packages/contracts` 是全系统唯一的 DTO 事实源（26 个模块，TypeBox schema），设计正确；但它**没有任何测试**，schema 改动只能靠调用方运行时 `Value.Check` 兜底。`docs/02_architecture/HTTP接口与共享DTO协议SDD.md` 要求产出 OpenAPI，当前仓库**没有从 schema 生成任何产物**。

**建议**：为契约补 schema 单测（成功/失败样例），并接入 `ts-json-schema-generator` 或同类工具，从 schema 生成 OpenAPI 与前端类型，杜绝"契约与实现各写一遍"。

## 四、可读性

| 问题 | 证据 | 建议 |
| --- | --- | --- |
| 行宽失控 | dispatcher.ts 最长单行 962 字符，39 行超 200 字符 | 引入 Prettier（printWidth 120）并对超长文件分片 |
| 错误码丢失类型 | `throw new Error(WalletErrorCode.X)` 模式 **250 处**，`Error` 只保留字符串 message，调用方只能靠字符串比较分支 | 定义 `class DomainError extends Error { code: DomainErrorCode }`，或用带判别字段的结果类型（如 `{ ok: false, code }`）替代异常流 |
| 静默吞错 | 空 `catch {` **147 处**，`catch (error)` 未处理 **46 处**；资金路径（钱包/金币集市）也在其中 | 允许吞错时必须写明理由注释（best-effort / 可降级），否则改为向上返回错误码 |
| 编码风格混用 | 同一文件里 `try { return JSON.parse(text) as unknown; } catch { throw new Error('INVALID_JSON'); }` 与多行风格并存 | 由 Prettier 统一，风格争论一次性结束 |
| 命名歧义 | `apps/admin/src/platform/agent-downlines/agent-audit-application.ts` 位于 agent-downlines 目录；`local-demo-social-seed.ts` 与 `local-demo-admin-users.ts` 两套演示数据 | 目录即归属，文件名与目录名对齐 |

## 五、可理解性

| 问题 | 证据 | 影响 |
| --- | --- | --- |
| 注释密度过低 | 业务层（web/platform + admin/platform + packages + games）合计仅 **41 行中文注释 + 37 行英文注释**，对应上万行含金额语义的逻辑 | 5% 手续费、冻结期、流水门槛、幂等键、系统账户分录、返佣层级等规则**在代码里没有一句解释**，只能回查 43 份文档 |
| 文案硬编码 | web + admin 中约 **3.3 万处中文词元**散落在组件与测试里，无 i18n 层 | 五端（iOS/Android/Windows/macOS/Linux）+ 前后台多语言时必然漂移，运营改文案要改代码 |
| 演示数据与真实数据同构 | 后台 `local-demo-admin-users.ts` 等文件里直接写"演练玩家·海风"、"DEMO91001" | 演示数据与领域模型共用同一 DTO，缺少 `source: LOCAL_DEMO` 之外的统一隔离约定 |
| 测试覆盖面偏科 | web/admin 组件测试较密，但 `packages/contracts` 0 测试、`games/shisanshui/client` 0 测试、`apps/server` 仅 3 个用例（6 个路由） | 契约、牌桌渲染、服务端路由三处最易回归的地方没有关卡 |

**建议**
1. 在资金与资产相关模块写"规则注释"：每个费率、阈值、冻结期、幂等策略写明**规则来源文档链接 + 口径一句话**，例如 `// 提现门槛 1000 枚金币等值且为门槛正整数倍，见 docs/04_domains/支付渠道流水要求与直连归因.md`。
2. 引入轻量 i18n（玩家端文案优先）：先把集中在组件里的**玩家可见**文案抽到 `locales/zh-CN/*.ts`，后台与内部调试文案可暂缓。
3. 演示数据统一收敛到 `demo/` 命名空间并集中一个 `source` 常量，与真实适配器在类型层面区分。
4. 补三处测试：`packages/contracts` schema 单测、`games/shisanshui/client` 牌桌渲染单测、`apps/server` 每个路由一个用例。
