# 架构评估与落地方案

评审日期：2026-10-08。前提：[已确认的技术架构](./技术架构决策说明.md)。本文细化实现取舍；目录以 [项目结构规划](./项目结构规划.md) 为准，下载机制以 [网络预加载设计](./网络预加载设计.md) 为准。当前只有文档，没有已运行系统；指标均需后续验证。

## 1. 评估结果

现有方向可行，建议采用 **Vue/H5 应用外壳 + 按需启动的 PixiJS 游戏 + Koa/Socket.IO 模块化单体 + MySQL 权威记录 + Redis 临时协调**。移动端建议 Capacitor，桌面端建议 Electron。先完成单实例闭环，同时保留房间路由、控制权与幂等接口，再验证两万在线的多实例形态。

| 决策 | 评估 | 进一步落实 |
| --- | --- | --- |
| 全部非游戏页面 H5 | 合理 | web 与 admin 独立构建，游戏入口动态加载 |
| Vue 领域拆分 | 合理 | 先在 packages/backend 内部划分模块，不把每个领域立即做 workspace 包 |
| HTTP + Socket.IO | 合理 | 一个 Manager；命令超时不等于业务失败 |
| Workbox + 自有调度 | 合理 | 缓存与调度分离，网络余量控制，单一请求协调器 |
| MySQL + Redis | 合理 | SQL 事务负责资产与关键事件；Redis 缓存可重建 |
| 五级邀请/代理 | 可实施 | 关系变更串行化，Admin 子树换绑与审计 |
| 两万在线 | 需容量验证 | 连接、房间、CPU、SQL、Streams 分别测量 |
| 全 AI 美术 | 可实施 | AI 母版 + 程序组合 + 编码/图集/格式验收 |
| 五端封装 | 可实施 | 共用业务代码，分别构建与验证；App 安装包体单独预算 |

大陆 IP 路由到用户提供的优化云主机作为既定部署边界，不重新讨论线路采购。应用节点无论从哪个入口接入，都使用统一身份、钱包与 room owner。

## 2. 首版工具取舍

以下为建议采用项，版本在真正初始化依赖时核实并锁定，本文不冒充已经安装或确认了每个包的最新补丁。

| 层 | 建议 | 依据与理由 |
| --- | --- | --- |
| workspace | pnpm；内部依赖 workspace:* | 官方原生支持 workspace，避免内部包误解析到 registry |
| 前端 | Vue 3、Vue Router、Pinia、Vite | 路由按需加载，领域 store，降低首包 |
| 游戏 | PixiJS 稳定版，独立规则包 | 图形模块只进入游戏 bundle |
| 缓存 | vite-plugin-pwa injectManifest、Workbox | 自定义预缓存清单和游戏资源策略 |
| 协议校验 | Zod Mini 的共享 schema | 严格网络字段校验且有 tree-shakable API；用本项目 bundle 测量验证收益 |
| 数据访问 | Sequelize + mysql2 | 用户指定 ORM，MySQL 方言驱动；显式事务/锁与规范化迁移 |
| Redis | 官方 Node 客户端 + Redis Streams adapter | 与 Socket.IO 恢复能力集成 |
| 测试 | Vitest、Playwright、真实 MySQL/Redis 集成环境 | 规则/用例、浏览器流程和数据库竞态分层验证 |
| 边界检查 | dependency-cruiser + ESLint | 检测循环依赖和 browser/server 禁止关系 |

pnpm 用 workspace 协议控制内部解析；Vue 官方性能指南支持代码拆分；Zod Mini 面向更严格包体约束。[pnpm workspace](https://pnpm.io/workspaces)、[Vue 性能指南](https://vuejs.org/guide/best-practices/performance.html)、[Zod Mini](https://zod.dev/packages/mini)

用户指定 Sequelize ORM，mysql2 作为方言驱动；不再使用 Kysely。Model/迁移显式表名、引用字段、注释、unsigned ID 与 DATETIME，UnitOfWork 显式共享 Transaction。ORM 不自动保证资金锁/幂等正确性，必要 SQL 通过 sequelize.query 保持同事务，见 [数据库规范](../05_data/数据库设计规范与Sequelize方案.md)。[Sequelize 事务](https://sequelize.org/docs/v6/other-topics/transactions/)、[mysql2](https://sidorares.github.io/node-mysql2/docs)

首版不增加微前端框架、动态远程代码联邦、Kubernetes 或机器学习带宽预测。workspace 脚本按依赖顺序构建即可；若构建耗时实测成为问题，再引入任务缓存工具。外部游戏仅实现稳定 Stub。

## 3. 前端与游戏运行边界

Vue 页面以领域组织：identity、lobby、wallet、referral、history、settings；每域有 routes/pages、store、use-cases 和 API 映射。共享 UI 不依赖业务 store。HTTP/Socket 的原始数据经 schema 校验后更新领域状态，组件不直接调用转账 SQL 或处理计分规则。

Pinia 管理用户可见的权威快照副本；钱包只通过 HTTP 查询/已提交推送更新，不从客户端动画计算余额。PixiJS 的 Texture、Container、Application 使用游戏模块自身管理，不进入深度响应式 store。可用 shallowRef/markRaw 或闭包持有运行对象，避免 Vue 对显示树做深层观察。[Pinia store](https://pinia.vuejs.org/core-concepts/)、[Vue 性能指南](https://vuejs.org/guide/best-practices/performance.html)

```text
游戏加载：manifest → P1 已可用 → dynamic import → mount → ready → 准备/开局
游戏退出：停止输入 → 取消订阅/异步任务 → 销毁动画/renderer → 释放资源句柄 → 回子厅
```

mount/unmount 必须可反复执行；路由跳转失败、加载取消、WebGL context lost、App 切后台和重连快照都要有明确状态。renderer 恢复只重建显示，不重新参加牌局。资源句柄按引用计数或所有权释放，共享图集仍被另一场景使用时不能全局卸载。

Game SDK 暴露视图快照、受限命令、资源句柄、导航与日志，不暴露数据库或任意钱包写入口。用户可见规则计算可共享；服务器持牌、控制权和随机牌序不进入客户端包。

## 4. 跨领域事务与资产

边界不等于每个领域使用不同数据库。首版共享一个 MySQL 权威库，由应用编排层在同一 UnitOfWork 中调用 wallet、room、matchmaking 的公开事务参与接口；仓储适配器使用同一个数据库连接。不得让每个用例自行开始嵌套的独立事务，造成“钱包冻结成功但房间没有创建”。

### 4.1 开局事务

匹配 Redis 原子领取四人后生成唯一 matchId；应用进入事务，锁定四人的 active membership，校验唯一归属、当前档位/规则版本和准备/资源状态；按 userId 固定顺序锁钱包，检查余额范围与可用额；创建 round、冻结 holds、保存牌序与截止配置、写 outbox，提交后才发牌。

Redis 队列状态是发现和调度依据，数据库 active membership 才是防重复入局的最终约束。事务失败回退领取；领取租约过期不直接重开已持久化 matchId。房间等待状态可先建立，冻结只在正式开局事务发生。

### 4.2 钱包不变量

- 金额为整数，HTTP/Socket 用十进制字符串；内部用 bigint 或安全金额类型，禁止先 Number 再转换。
- 玩家金币/人民币可因已审计冲正或追回为负，但 frozen 始终非负且不超过 `max(balance, 0)`；负余额不能消费、下注、转账、兑换或提现，后续入账先抵扣欠额。系统 CNY 仍非负；系统金币发行账户允许负余额且 frozen 固定为 0。holds 的有效金额和账户 frozen 必须一致。
- 内部转移每种资产分录合计为 0，系统为赠币/返点/兑换/费用的来源归宿；外部入金/出款按净流入流出核对，不要求内部余额变化为 0。系统金币负余额代表发行记账，不代表可以透支人民币；玩家负余额表达账务冲正/追回形成的欠额，见 [系统账户设计](../04_domains/系统账户与资产记账设计.md)。
- 业务幂等键唯一且保存请求摘要，同键不同内容返回冲突。
- 状态/流水/walletVersion/outbox 在同一事务更新；通知只能发生在提交之后。

建议增加 `wallet_holds`，唯一 `(round_id,user_id)`，冻结/释放不是余额扣减；未结算作废释放同一 hold，重复释放无副作用。钱包净余额可由初始记录和有效分录重建，日常核对物化余额与账本。

### 4.3 锁顺序与未知提交

约定：授权门禁（仅需时）→ 操作幂等记录 → active memberships（仅需时）→ room ownership（仅需时）→ round（仅需时）→ 邀请关系/流水状态（仅需时）→ 金币/余额账户（资产类型/userId/currency 排序）→ holds/entries/allocations/outbox。客损由代理线下结算，不存在平台客损状态锁。所有路径遵守相同顺序，事务内不调用 Redis、Socket、外部 HTTP 或做自动摆牌搜索。死锁按同一幂等键重试整个事务，设置最大次数和退避。[MySQL 锁定读](https://dev.mysql.com/doc/refman/9.7/en/innodb-locking-reads.html)、[死锁处理](https://dev.mysql.com/doc/refman/9.7/en/innodb-deadlocks-handling.html)

数据库连接在 commit 附近断开时，结果属于“未知”，不是默认失败。客户端以原 operationId 查询；服务端从唯一记录恢复，不创建新操作补扣款。Admin 补偿引用原操作并写新分录，禁止修改旧 entries。

outbox 由 worker 按租约领取，发送后标记完成。发送成功但标记失败可造成重复通知，因此消费端按 eventId/walletVersion 去重。outbox 的完成仅表示已派发，不表示客户端已永久收到；查询接口仍是恢复入口。

## 5. 房间权威与 Socket.IO

首版采用“每应用节点管理一组房间 actor”的执行方式，单房间命令串行。room-runtime 模块提供路由端口，阶段 B 可本地调用；阶段 C 多节点经受认证的内部 RPC 调用 owner。Redis Streams adapter 用于 Socket 消息分发，不充当房间命令总线或锁。

Redis 保存带 TTL 的当前房间租约；`room` 行保存 ownerKey 与 fencingToken。新 owner 获得 Redis 租约后，先在数据库事务中递增 fencingToken，再开始处理。每次关键写入校验 `round.fencingToken` 与 `room.fencingToken`，因此旧节点即使恢复也不能继续提交或结算。租约续期不频繁写 MySQL。

读写持牌/成功提交均为私有数据；公共快照只包含座位与阶段。在 COMPARING 开放后才发布允许公开的三墩。请求身份取自验证会话，不能接受 payload.userId 作为执行者。

### 5.1 截止边界修订

截止判定定义为“命令在权威 owner 完成基本解析并登记入队时的服务器时间”，不是客户端时间或操作系统网络接收时间。`admittedAt < deadlineAt` 有效；等于截止无效。已登记的有效提交先串行处理，截止命令以 barrier 入队，不跨过已有有效提交。转发到 owner 的内部排队属于系统延迟，纳入监控与容量预算。

提交持久化失败不成功 ACK；若之前已成功持久化但 ACK 丢失，则重复请求返回原提交。超时兜底使用预先计算的合法方案；不在计时器回调里同步搜索四人的全部排列。

### 5.2 版本与序号

`protocolVersion` 表示通信兼容；`ruleVersion` 表示玩法；`configVersion` 表示档位快照；`roundId` 表示业务局；`stateVersion` 表示房间状态版本；`walletVersion` 表示余额副本版本；`ownerEpoch` 表示写入控制权。这些字段不得互相替代。

全量内部 eventSeq 可递增，但授权过滤后的客户端不一定收到每个内部事件，不能用“stateVersion 跳号”认定丢包。需要增量恢复的公开/私有订阅建立自己的 streamId + seq；不确定时用最新权限过滤快照替换。Socket.IO 的恢复 offset 与业务 seq 分开维护。

共享 Manager 仅在相同 origin/path、相同连接配置时复用；封装 App 的本地 origin、Cookie/CORS 与真实请求路径须集成测试。polling 需要负载均衡粘滞，代理超时大于心跳窗口；Redis Streams 恢复留存按事件速率核算，不采用无限恢复窗口。[Socket.IO 多节点](https://socket.io/docs/v4/using-multiple-nodes/)、[客户端配置](https://socket.io/docs/v4/client-options/)、[Streams adapter](https://socket.io/docs/v4/redis-streams-adapter/)

## 6. 数据与协议规划

实际迁移以 [数据库规范与 Sequelize](../05_data/数据库设计规范与Sequelize方案.md) 为准：全部独立 unsigned bigint id、非零状态、三个 DATETIME 与注释，单数 snake_case 表及精确引用名。下表是领域概念，旧复数表及多角色前缀 ID 草案不能直接建库。

| 域 | 权威数据 | 主要约束 |
| --- | --- | --- |
| identity | user、device、recovery_credential；会话在 Redis | user 保存登录资料和 TOTP；device 含当前设备凭证；恢复二维码凭证保留历史且每账号仅一条有效 |
| wallet | wallets、operations、entries、holds、transfers | 操作唯一、金额合法、版本递增、分录守恒 |
| payments/双资产 | SDD 定义的 `order`、`payment_event`、`external_settlement`、`coin_exchange`、`asset_account`/`asset_entry`/`asset_hold`、`payout_account`、`withdrawal`、`payout_attempt` | 统一资产账本、兑换原子、支付去重、占款冻结、未知出款不重付 |
| referral | referral_binding、referral_binding_event、referral_reward_allocation | 固定四级祖先列、本人加四级上级共五层、Admin 换绑、防环、返点幂等 |
| catalog/configuration | game、game_tier、game_config、system_config 当前值；变更由 admin_audit_event 审计 | 配置校验、缓存失效及牌局生效时不可变快照；不单独建配置版本表 |
| room | memberships、rounds、players、events、ownership | 单归属、提交唯一、epoch 门禁 |
| jobs | outbox、job_leases | 可重试、幂等、失败原因可查 |
| admin/history | user 上的 Admin 权限码 JSON、admin_permission 路径目录、audit、查询投影 | 记录操作来源，权限码可直接按管理员配置 |

全表包含 created_at/updated_at/deleted_at/status；所有状态非零且使用领域常量，流水/审计不因存在 deleted_at 而允许删除。IP 归因、reward_type、四个上级比例和奖励冻结见 [邀请归因返佣与数据规范](../04_domains/邀请归因返佣与数据规范.md)；已确认的充值购买金币、返点入余额、兑换后提现见 [双资产方案](../04_domains/双资产充值兑换与提现.md)。

JWT 与服务端撤销见 [JWT 设计](../04_domains/JWT登录与会话设计.md)。客损由代理线下结算；直属上级为客损模式的客户不使用平台充值、兑币及提现，祖先链上级可在平台内向其供币。普通赠币金币统一使用、有效下注流水要求限制提款/转出。余额 CNY、TRON USDT、代理方式、默认 1:10、1000 枚整数倍和身份三选一见 [最新方案](../04_domains/支付渠道流水要求与直连归因.md)。

HTTP 使用 `{requestId, code, message, data, serverNow, details?}` 响应 envelope，并同时返回匹配的 HTTP status 与稳定业务错误码；状态映射、DTO 单一来源和共享 schema 见[HTTP 接口与共享 DTO 协议 SDD](./HTTP接口与共享DTO协议SDD.md)。Socket 命令补 `roundId/commandId/protocolVersion`，ACK 包含接受/拒绝及权威状态。错误至少细化为余额不足、冻结不足、阶段过期、资源版本不兼容、重复归属、关系超深、权限不足和操作结果未知。

schema 只输出公开 DTO；服务端表结构不是协议类型，数据库 bigint/日期/内部枚举通过明确映射转换。Admin contracts 独立于玩家 contracts，不从一个总 barrel 自动导出所有操作。前端校验改善交互，服务端校验负责权威。

## 7. 五端与资源流水线

Capacitor 与 Electron 共用 web 构建产物，容器只实现平台端口。移动端通过 webDir 打包已构建资源；本地 origin 到远程 API 的认证策略要与浏览器同站 Cookie 区分，不在生产以远程 server.url 替代完整打包策略。[Capacitor 配置](https://capacitorjs.com/docs/config)

Electron bridge 只开放具名能力；Linux safeStorage 的可用后端取决于环境，检测不到安全加密存储时明确降级为不持久保存刷新凭证，不能把弱保护当系统保险箱。[Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)、[Electron 安全](https://www.electronjs.org/docs/latest/tutorial/security)

AI 源文件留在 assets/source，生成配置在 provenance，WebP/AVIF/HEVC 与后备格式由工具构建；manifest 指向具体 hash/variant，客户端下载一份。App 安装包包含核心资源但 Electron 自带运行时，安装包大小不能等同 H5 P0 或 PixiJS 增量。

素材生成必须调用 AI API，由独立内部工具与执行器管理，凭证不进入 web/App，生成任务不占用游戏实时服务。具体任务与发布边界见 [AI 素材接口生产方案](../07_assets/AI素材接口生产方案.md)。
