# 架构复用与硬件加速审视

日期：2026-10-10。本文对当前 monorepo、客户端、实时服务、媒体资产、数学模拟和 Docker 规划做“复用优先”审查，目的是减少自研基础设施，把研发投入集中在游戏规则、资产账本、运营规则和产品体验这些本项目真正独有的部分。

## 1. 结论

当前规划大方向正确：Vue/PixiJS、Workbox、Socket.IO、Sequelize、Redis Streams 和 Docker 都采用成熟组件；仍要守住三条边界：

1. **平台提供的能力直接用平台 API/成熟库，不自行实现渲染器、缓存协议、密码算法、媒体编解码、队列/ORM。**
2. **只为本项目业务写薄的领域层和适配层。** 自研的核心应是牌局规则、资产守恒/业务操作、上级模式授权、游戏数学模型、配置预检和有限的资源优先级策略；它们不能由通用库替代。
3. **硬件优化要靠 profile 验证。** 默认利用浏览器 GPU、原生媒体解码、Web Crypto 和 CPU worker；不要在没有设备实测数据时写自定义 GPU shader、WASM codec 或跨端渲染器。

### 2.1 优先采用而不要再抽象一层的组件

- `resource-runtime` 可以继续作为薄 package，但内部应直接调用 Workbox、Fetch、Cache Storage、Resource Timing 与浏览器能力检测，不要把这些再包成一套“通用下载平台”。只把游戏资源 manifest、唯一任务 key、前台优先级提升、并发上限和弱网降速策略作为本项目代码。
- Socket.IO 多节点 adapter 以官方 `@socket.io/redis-streams-adapter` 为当前候选。它是跨节点广播和短时 connection-state recovery 组件；长期消息、活动公告补拉、客服历史和游戏权威快照仍来自 MySQL/HTTP。Socket.IO 默认服务端事件不是 durable delivery，断线游标、ACK 和幂等必须由应用层定义。[Socket.IO Redis Streams Adapter](https://socket.io/docs/v4/redis-streams-adapter/) [Delivery Guarantees](https://socket.io/docs/v4/delivery-guarantees/)
- Workbox/vite-plugin-pwa 管 SW precache/runtime cache、cache version 和请求策略；游戏专属后台下载由一个轻量 coordinator 排序即可。不要让 SW 与页面各自下载相同资源，也不要缓存钱包、账号、私牌或 Admin API。[Workbox](https://developer.chrome.com/docs/workbox/what-is-workbox) [vite-plugin-pwa](https://github.com/vite-pwa/vite-plugin-pwa)
- PixiJS 使用现成 Assets、Ticker、interaction、scene graph 与 GPU renderer。十三张的拖拽、吸附、自动摆牌预览和动画可在 Pixi primitives 上实现；不需要另买/另造完整游戏引擎。其他游戏插件只提供 host lifecycle 与窄契约，不能先建一套自定义通用玩法 DSL。
- 监控从服务端 OpenTelemetry traces/metrics 开始，加入 trace ID、round/session/operation correlation ID；浏览器采集只记录必要的资源加载时长/失败和渲染性能，默认不开全量用户行为录制。OpenTelemetry JS 对 Node traces/metrics 稳定，浏览器自动 instrumentation 仍需谨慎评估。[OpenTelemetry JS](https://opentelemetry.io/docs/languages/js/)

### 2.2 该自己做的部分

- 游戏本身规则和权威 handler：十三张判型/摆牌/结算，以及以后 Slot、捕鱼、定时开奖各自 handler/math model。这些是产品规则，不存在能正确替代本项目配置的通用引擎。复用纯算法/标准统计方法，不复用错误的“统一 RTP 模型”。
- 资产账本和跨资产用例：asset operation/entry/hold、充值兑换提现、幂等和事务是自有财务语义，必须自己定义并测试，但只基于 Sequelize/MySQL transaction 编排，不自制数据库/账本引擎。
- 配置期望计算器：后台流程、指标口径、候选参数约束和审计属于项目业务；每个游戏实现纯 `GameMathModel`。模拟任务调用已有规则代码，统计区间可采用经过验证的统计库/公式，不造通用“博彩数学平台”。
- 平台事件与公告：事件类型、用户脱敏、主体排除、场景范围属于本项目规则；用既有 outbox/Socket.IO/配置 schema 实现，不做可执行脚本或任意规则表达式平台。
- 独特资源队列策略：现有需求确实有按网络估算做闲时下载。只实现资源优先级和调度决策，并把 cache、HTTP、hash verification 与后台执行委托给 Workbox/浏览器；不自制 Service Worker 栈。

## 3. 可利用的硬件与系统加速

| 工作负载 | 加速来源 | 规划方式与限制 |
| --- | --- | --- |
| PixiJS 牌桌/Slot/捕鱼画面 | GPU：WebGL/WebGL2；WebGPU 可选 | 生产默认 PixiJS WebGL renderer；WebGPU 经 capability detection 和目标设备实测后再灰度。PixiJS 当前文档称 WebGL 稳定且推荐生产，WebGPU 仍有浏览器实现差异。[PixiJS Renderers](https://pixijs.com/8.x/guides/components/renderers) |
| 卡牌/头像/装饰纹理 | GPU texture upload、batching、atlas | 复用 PixiJS renderer 和 texture cache；控制纹理尺寸、同图集材质与滤镜数量；不能把大量静态牌面每帧重新生成 Canvas。 |
| H5 图片渲染 | 浏览器原生 image decoder/GPU compositing | `<img>`/ImageBitmap 与 CSS transform 优先；图片分辨率按设备像素比和视口选择，低端机降低渲染分辨率。解码使用浏览器能力，不加载 JS 解码器。 |
| 动图/短视频 | OS/浏览器硬件视频解码器 | 默认使用 `<video>` 播放，让浏览器解复用/解码；通过 `MediaCapabilities`/`canPlayType()` 探测是否支持和是否流畅。WebCodecs 仅在需要逐帧控制时用，且必须 feature-detect；H.265 在浏览器/平台/硬件上的支持并不一致，保留目标编码同时生成兼容 fallback variant。[MediaCapabilities](https://developer.mozilla.org/en-US/docs/Web/API/Media_Capabilities_API/Using_the_Media_Capabilities_API) [WebCodecs](https://developer.mozilla.org/en-US/docs/Web/API/WebCodecs_API) [HEVC 支持/选择](https://developer.mozilla.org/en-US/docs/Web/API/WebCodecs_API/Codec_selection) |
| 客户端文件加密/解密 | 浏览器 Web Crypto，由底层浏览器/OS/CPU 实现优化 | `SubtleCrypto` 放 Dedicated Worker 执行大块/分块运算，避免主线程卡顿；AES-CTR 与逐块 HMAC 按已确认格式使用 Web Crypto，不自行实现 cipher。Web Crypto 支持 AES-CTR，也提示 CTR 不自带认证，当前约定的 HMAC 是必要配套。[Web Crypto encrypt](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/encrypt) |
| Node 侧加密/哈希 | Node `crypto`/OpenSSL 与系统密码学实现，可能利用 CPU 指令集 | 使用 Node 官方 crypto；运行时和底层库负责 AES/SHA/随机数实现。不要手写 AES-NI/SIMD。硬件加速是否生效取决于平台构建，按部署镜像 benchmark，不以此作为安全假设。 |
| 1000/10000 局游戏模拟 | 多核 CPU | Admin 浏览器用 Dedicated Worker；Node 服务端用有界 `worker_threads` pool 或独立 worker 容器。Node 官方指出 worker_threads 面向 CPU-intensive tasks，I/O 工作仍用异步 API。[Node worker_threads](https://nodejs.org/api/worker_threads.html) 不把真钱账本、RNG 权威结果或下注处理迁入 GPU。 |
| 图片缩放/格式转换 | CPU SIMD/多线程原生库、可能的硬件编解码 | AI 母版后处理在 Docker 内用 Sharp/libvips 与 FFmpeg；批处理资源不占在线游戏 worker。发布时离线产出高/中/低 variants，客户端只下载匹配档位。 |
| MySQL/Redis | CPU、内存、SSD/NVMe 与网络 | 给 MySQL 合理 buffer pool/连接池和可靠持久盘；Redis 分清持久 streams 与临时缓存。容量依赖压测、查询索引、事务持锁时间，不应为账本引入 GPU 数据库。 |

PixiJS v8 renderer 的硬件加速是既有能力：建议 WebGL 作为稳定默认，WebGPU 作为实验/灰度路径；`powerPreference: high-performance` 只在实际牌桌可测得收益时开启，省电设备可能应选默认策略。把 GPU 帧时间、掉帧率、纹理内存与设备档位纳入客户端 perf metrics（仅采集匿名必要数据）。[PixiJS Application options](https://pixijs.com/8.x/guides/components/application)

## 4. 资源网络估算的现实边界

- 可采集数据：Resource Timing 的 DNS/connect/TTFB/responseEnd、资源字节数、完成速率、timeout/retry、成功/失败、前台加载耗时；支持时读取 `navigator.connection.effectiveType/downlink/rtt` 作为额外提示。
- `Network Information API` 的 `downlink` 是应用层带宽估计且有量化舍入，接口并非所有浏览器都支持；只能作为一个输入，必须有基于真实资源请求的 fallback。[NetworkInformation downlink](https://developer.mozilla.org/en-US/docs/Web/API/NetworkInformation/downlink) [Resource Timing](https://developer.mozilla.org/en-US/docs/Web/API/Performance_API/Resource_timing)
- 浏览器页面 JS 不应宣称能从普通 HTTPS transfer 精确测出 TCP packet loss/retransmission。TCP 重传等数据由系统/网络栈处理，并非网页 Resource Timing 的标准字段。使用端到端下载吞吐、RTT、错误/重试和连续 stall 作为**弱网质量信号**，输出保守调度档而非“真实丢包百分比”。需要真实丢包诊断时用服务端/网络设备指标或专门的测试环境。
- 不要通过反复下载测速文件探测带宽；用自然业务资源样本做滑动窗口和置信度，限制采样体积，并尊重省流量模式、Save-Data（若可用）、页面前台交互和用户设置。
- 调度降级要确定：`critical game chunk` > 当前游戏首屏纹理/音效 > 当前厅封面 > 其他游戏预取；网络慢/错误率升高/前台用户开始操作时暂停非必要下载。Workbox Cache Storage 保证缓存和版本策略，scheduler 只决定何时发任务。

## 5. 依赖审查结论

### 继续采用

Vue 3/TypeScript/Vite、Element Plus、PixiJS 8、Koa、Socket.IO、官方 Redis Streams Adapter、MySQL、Redis、Sequelize、Umzug、Workbox + vite-plugin-pwa、pnpm workspace、Docker Compose/BuildKit，以及浏览器 Web Crypto。

### 初始化时做小型验证后再锁定

- **运行时 schema**：挑一种主 schema 体系，证明同一 schema 能用于 Koa 请求验证、Socket 命令、DTO 类型推导与 OpenAPI 输出；不要合同类型、validator schema、OpenAPI 三份手写。
- **网络资源 scheduler**：先做浏览器原型测吞吐/缓存命中/弱网暂停；Workbox 负责缓存，验证 Service Worker 和页面间消息在目标浏览器的可靠性。不要先上复杂多标签调度框架。
- **OpenTelemetry exporter/后端**：API 与 worker 先打通 traces/metrics 到本地 Docker observability profile，再选托管/自托管后端；浏览器 telemetry 先有限采样。
- **AVIF 动图、HEVC 视频及音频编码**：在 iOS Safari、Android Chrome/WebView、Windows/macOS 浏览器矩阵做真机可解码/平滑性/体积测试；每种内容必须有清楚的 fallback/静态降级策略。
- **worker pool 与 worker queue**：1000/10000 次模拟若经 benchmark 不阻塞 Node event loop，再确定使用同进程 bounded pool 还是独立容器 worker。不要为尚未出现的工作量先加 Kafka/RabbitMQ。

## 6. 不建议当前引入的重量级基础设施

- 不拆微服务、不加 Kubernetes/Kafka/通用规则 DSL/独立配置中心，直到团队规模、压测或故障域证明模块化单体不够。
- 不引入第二个实时通信/聊天平台来管理用户好友和资产附件；它会复制身份、会话和权限边界。首版用现有 Socket.IO、MySQL、outbox、asset 与社交用例实现简单私聊/社区。
- 不上通用 ECS/物理引擎/动画编辑器；十三张牌局不需要，未来 Slot/捕鱼再按具体需求选成熟游戏 SDK/模块，不预先建大而全引擎。
- 不为“硬件加速”重写 WebGL renderer、WASM 加密、WASM 图片解码、GPU 概率模拟；先用现成 GPU renderer、Web Crypto、原生 codecs 和 CPU worker，再用真实 profile 找瓶颈。
- 不在客户端运行财务结算或权威概率；GPU、SIMD、浮点优化都不能改变服务器数学结果与资产账本。

## 7. 建议落入实施阶段的质量门槛

1. 依赖选择先用官方/上游维护的组件，新增基础设施依赖必须写明无法复用既有能力的原因、维护者、许可证和运行时成本。
2. 游戏模块契约要经过一个十三张端到端纵向切片验证；更多抽象在至少第二款不同运行模型游戏接入后再提炼。
3. 给 PWA cache、资源 scheduler、Socket command envelope、worker pool、asset cipher 和 game module registry 各写一个可运行小样，验证浏览器/App/WebView边界后再大规模铺开。
4. 每次性能工作先产出 profile：CPU flamegraph/event loop delay、浏览器 Performance/Canvas/GPU 帧耗时、资源传输字节数、内存/纹理使用；无 profile 不加入复杂优化层。
5. CI 做依赖 license/vulnerability、SBOM、镜像扫描与 secrets scanning；依赖升级先跑 lockfile、schema contract、弱网与目标设备测试。
