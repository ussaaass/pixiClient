# 项目结构规划

日期：2026-10-08。本文为目录与依赖的最终规划，替代早期报告中的目录草案。列出的目录是待初始化目标，当前不表示这些应用已经创建。阶段顺序见 [架构评估](./架构评估与落地方案.md)。

## 1. 结构原则

应用入口负责装配，包负责可复用能力，领域负责业务规则。首版不把每个领域拆成独立 npm 包：后端放在一个 Node-only backend 包，内部划分模块，HTTP/Socket 与 worker 入口都引用它；浏览器领域放在 web 内部。纯十三张规则与 PixiJS 客户端分为不同包，防止浏览器误引入服务器实现。

采用 **pnpm workspace** 管理 monorepo，内部依赖用 `workspace:*`；仅给真实构建/复用边界设置 package.json。`apps/admin` 固定使用 **Vue 3 + TypeScript + Vite + Element Plus**，独立构建/部署；Element Plus 组件按需引入并执行 tree-shaking，图表依赖只放在对应后台 feature chunk。官方 Vite 提供 Vue/TS 模板，Element Plus 支持按需组件导入。[pnpm workspace](https://pnpm.io/workspaces)、[Vite](https://vite.dev/guide/)、[Element Plus Quick Start](https://element-plus.org/en-US/guide/quickstart)、[TS Project References](https://www.typescriptlang.org/docs/handbook/project-references.html)

## 3. 后端模块内部约定

```text
modules/wallet/
├── domain/                         Money、Wallet、Operation、业务不变量
├── application/                    TransferCoins、HoldForRound、SettleRound
├── ports/                          仓储、事务参与、时钟与幂等接口
├── adapters/                       MySQL 查询、投影与映射
├── public.ts                       其他模块允许使用的用例/接口
└── *.test.ts
```

只在职责真实存在时分文件，不为每个简单函数创建抽象类。业务端口不传 Koa ctx、Socket 对象或 mysql2 连接；事务由 infrastructure 创建并向已装配仓储提供统一作用域。HTTP/Socket 层只做认证、校验、调用公开用例和响应映射。

ORM 使用 Sequelize + mysql2；infrastructure/database 规划 models、sequelize-instance、unit-of-work、migration-storage，领域仓储仅在适配层依赖 ORM。公共域端口不暴露 Sequelize Model/Transaction，所有跨域资金操作共享同一 Transaction；模型/迁移/关联字段和注释遵循 [数据库规范](../05_data/数据库设计规范与Sequelize方案.md)。

共享代码分层：`packages/contracts` 放玩家端跨 HTTP/WebSocket 消费的 schema、DTO、枚举常量和由 schema 推导的 TypeScript 类型；`packages/admin-contracts` 放后台专属 DTO/schema；`packages/domain-kernel` 只放纯函数、值对象、单位换算及没有 Node/浏览器依赖的稳定领域常量。单一领域规则优先留在 backend/game domain，不为“复用”把业务逻辑搬到前端。前后端可共用接口/类型/常量，但不能共用 Sequelize Model、ORM entity、数据库仓储或带副作用的 use case；浏览器把契约类型当作静态提示，服务端仍须运行时校验。TypeScript 没有 Rust 式 `trait` 语法；跨端扩展点用窄 `interface`/type contract 表达，避免继承型 mixin/共享实现造成隐式耦合。游戏专属协议和规则继续由 `games/<gameKey>/contracts|rules` 所有。

workflows 可以调用多个模块的 public.ts，但不能 import 私有 adapters；模块之间不得直接更新对方表。共享技术工具放 infrastructure，共享业务概念必须明确归属，避免出现承载全部业务的 common/utils 文件夹。接口分类、service/use case 职责、函数/class 取舍、Result 错误模式、事务 scope、依赖注入与测试规范详见[代码分层、接口与公共契约实施规范](./代码分层与接口实现规范.md)；HTTP envelope、状态码及 DTO/schema 单一来源见[HTTP 接口与共享 DTO 协议 SDD](./HTTP接口与共享DTO协议SDD.md)。

## 4. 包依赖与环境边界

| 使用方 | 允许依赖 | 禁止依赖 |
| --- | --- | --- |
| web | 玩家 contracts、UI、platform-client、resource-runtime、game-sdk；动态游戏入口 | backend、admin app/DTO、Sequelize/mysql2、Koa、Node fs |
| admin | admin-contracts、UI、公开基础协议、平台 HTTP 能力 | backend 源码、web store、游戏 renderer |
| game-host | game-sdk、game-protocol、resource-runtime、受控 registry | 具体游戏规则、wallet 仓储、Admin、远程任意 JS |
| 游戏 client | game-sdk、game-protocol、该游戏公开 contracts/rules、PixiJS（如需） | backend、原始 Socket、wallet 仓储、Admin |
| 游戏 server handler | game-protocol、该游戏 contracts/rules、backend 公开用例端口 | Koa ctx、客户端代码、Sequelize Model、直接改钱包表 |
| shisanshui-rules | 自身纯 TS 类型/算法 | Vue、PixiJS、Socket、DB、系统随机与时钟 |
| backend | 玩家/Admin contracts、rules、Node 适配器 | web/UI、PixiJS client、浏览器 DOM |
| server/worker | backend 公开 bootstrap/workflow 能力 | 其他 app 内部文件 |
| resource-runtime | 自身端口与 browser adapter；无业务 store | Vue、PixiJS、钱包模块、Node-only 实现 |
| mobile/desktop | web 构建产物、平台 bridge、资源清单 | 第二套玩法/计分/钱包实现 |

游戏引擎与游戏模块接口、客户端/服务端责任以及模块新增流程见 [游戏引擎与游戏模块边界](./游戏引擎与游戏模块边界.md)。平台的 game registry 是构建期白名单：

```ts
const registry = {
  shisanshui: () => import('@gameing/shisanshui-client'),
};
```

禁止 `export * from 所有游戏` 供大厅静态导入。注册表必须保留独立异步 chunk；资源清单提供预取 URL，预取只下载、不执行模块；dynamic import 仅在正式启动调用。服务端 handler 注册同样是构建期白名单，不能执行数据库提供的任意远程脚本。新增自研游戏不得要求修改大厅/钱包/房间核心实现。

contracts 按 subpath 导出，例如 `@gameing/contracts/wallet`；schema 构建规则一致，保留 type-only 导出。backend 标记 Node 环境且显式 exports，无对整个 src 的通配公开入口。依赖检查同时检查直接引用与传递路径；package exports 不代替 CI 检查。[dependency-cruiser](https://github.com/sverweij/dependency-cruiser)

TS 配置拆 browser（DOM、Bundler resolution）与 node（Node 环境、对应 ESM resolution），不能为全仓统一开启 DOM 和 Node 全局类型。引用项目采用 composite/build references；Vue 应用用 vue-tsc 核对 SFC，不能只跑 tsc 就宣称 Vue 页面类型全通过。

## 5. 资源协调器放在哪里

NetworkEstimator/PrefetchScheduler 的纯逻辑在 resource-runtime，页面生命周期和“常玩游戏”排序策略由 web 装配；SW 在 apps/web/src/sw，依赖同一 manifest/缓存约定。native 下载与安全存储由容器适配，公共逻辑不直接引用 Electron 或 Capacitor。

后台预取与前台 fetch 使用同一个资源 key 和协调器；SW 内网络请求去重，页面通过消息请求预取/升级任务。多标签由 SW 聚合，SW 不可用时以 Web Locks/BroadcastChannel 可用能力协调，无法协调则退回保守单页预取，正确性仍由 hash 缓存保证。共享缓存的下载状态不等于每个页面已完成解析/初始化。

manifest 构建工具读取 Vite 静态 imports/CSS 和资源配置，递归合并、去重，生成每游戏 P1/P2 入口；动态 imports 不盲目递归展开所有游戏。新 manifest 先验证 URL、variant、protocolVersion 和预算，再发布。[Vite manifest](https://vite.dev/guide/backend-integration)

## 6. 数据库与任务归属

迁移采用单一有序序列，注释领域所有权；公共 UnitOfWork 允许同一事务内操作多个域，不把迁移拆成各自不可控的顺序。生产迁移独立任务执行，不让每个 server 副本启动时并发改表。迁移兼容旧节点，优先新增/回填/切换/移除的多阶段流程。

建议 Umzug 调用 Sequelize QueryInterface，使用符合公共字段和注释规范的自定义 migration_history；不保留默认不规范 SequelizeMeta，不以 sync alter 代替迁移。未来 CI 加 schema-check，验证表名/引用、全表 unsigned bigint id、三个 DATETIME、状态及注释。系统账户 schema 统一采用 asset_account/entry/hold，取代此前 coin_wallets/cash_wallets 等物理表草案，见 [系统账户方案](../04_domains/系统账户与资产记账设计.md)。

worker 使用 backend 的 jobs/workflows 导出，不从 apps/server import handlers。房间 actor 首版随 server 启动；需要独立 room worker 时新增 app 入口并复用 backend runtime，不重写规则。自动摆牌 CPU 线程池是内部实现，不等同 outbox worker 进程。

## 7. Docker 与命令规划

Compose project name 固定 `gameing-hall-pixi`，profile 规划如下：

| profile | 服务 | 用途 |
| --- | --- | --- |
| 默认 data | MySQL、Redis | 本地开发数据依赖，具名持久卷 |
| dev | devcontainer、server、worker、web、admin、data | 所有 Node/pnpm/Vite 命令在开发容器内运行，源码 bind mount，依赖缓存使用独立卷 |
| full | server、worker、web、admin、data | 完整容器联调 |
| release-build | 多阶段 builder、静态 web/admin、server、worker 镜像 | CI/发布构建都在 Docker BuildKit 内完成，输出不可变镜像/artifacts |
| multi-node | proxy、两份 server、worker、data | sticky/Streams/room owner 接管 |
| network | 可控 HTTP/Socket 网络代理 | 丢包、断网、带宽/延迟变化 |
| observability | 指标与日志工具 | 压测与故障分析 |

“默认 data”是无 profiles 限制的基础服务集合，实际 profile 名仅给可选服务。Compose 顶层 name 与命令 `-p` 保持同值；数据库健康后执行迁移，再启动应用 readiness。depends_on 只协调启动顺序，不意味着持续健康监控，应用仍要处理依赖失效并报告不就绪。[Docker 项目名](https://docs.docker.com/compose/how-tos/project-name/)、[启动就绪](https://docs.docker.com/compose/how-tos/startup-order/)

首批施工已实现 `compose.yaml`：顶层 `name` 固定为 `gameing-hall-pixi`；默认启动 MySQL/Redis，`dev` 与 `full` profiles 按需启用开发容器和 H5/API；MySQL/Redis 使用显式 `external` 具名卷，因此 Compose `down -v` 不拥有删除权。`server/web/admin/dev` 各自使用固定命名的容器平台依赖卷，启动时在容器内执行 frozen install；pnpm store 单独挂载。源码仍 bind mount，但宿主机 `node_modules` 不再覆盖容器依赖目录，避免 Darwin 二进制进入 Linux 容器。依赖卷不是权威业务数据，重建后可通过 lockfile 恢复。仍需运维限制 `docker volume prune --all`/显式删卷，并配置容器外备份。当前 full profile 尚无 worker、migration job 或 release 镜像。

### 持久数据卷和防误回收约定

- 所有持久服务必须显式声明卷：开发环境采用 external 固定名称 `gameing-hall-pixi_mysql_data`、`gameing-hall-pixi_redis_data`，启动前显式创建；禁止匿名卷和将数据库目录写入容器 writable layer。Redis 若启用 AOF/RDB，也挂独立持久卷；缓存与会话若确定可丢失则单独配置，不能和 MySQL 数据卷混用。
- 发布 Compose 文件优先引用**部署前由运维创建的 external named volume**（或挂载到专用、持久的主机文件系统路径），不让应用栈生命周期创建/销毁权威数据卷。Compose 项目名固定并写进运行手册；数据库与 Redis 的 volume 名明确列出，不能依赖自动生成的匿名标识。Docker 官方说明命名卷独立于容器生命周期，但未被容器使用的卷仍可能被显式 volume prune 清除；external 不是备份，也不是对主机磁盘故障的保护。[Docker Volumes](https://docs.docker.com/engine/storage/volumes/)
- 生产数据至少每日加密备份到 Docker host 之外的独立存储，保留按恢复目标配置的时间点/日志备份；密钥与备份分离。升级镜像、迁移或改卷前执行备份；定期在隔离环境做恢复演练并记录 RPO/RTO。对 MySQL 使用一致性数据库备份/日志方案，不把运行中的数据目录裸拷贝当作唯一备份。
- 运行手册明确禁止对生产项目使用 `docker compose down -v`、`docker volume prune` 和 `docker system prune --volumes`；清理流程必须先检查卷名、挂载点、容器引用与最新备份，并由专用维护权限执行。普通发布只替换容器，不删除卷。
- 部署启动时校验实际挂载点、卷名、读写权限和剩余磁盘空间；健康检查监测数据库可用性、卷写入错误和备份新鲜度。容器重建、Docker daemon 重启、主机重启演练后验证数据库/Redis 恢复。 Docker daemon/主机/磁盘彻底损坏时，需从异机备份恢复，单靠本机卷无法防止数据丢失。
- 应用镜像使用不可变版本/tag；状态数据不放在镜像层或构建上下文。Dockerfile 和 Compose 分别为 dev/release 配置，生产不挂载源码；开发源码 bind mount 与持久数据库卷分开。

当前可执行子集：先复制 `.env.example` 到 `.env` 并替换开发密码；`docker compose --profile dev run --rm dev pnpm install` 安装依赖；`docker compose --profile full up --build -d --wait` 启动 H5、Admin 壳、API 和默认 MySQL/Redis，并等待健康检查；Admin 预览为 `http://localhost:10374`。类型和测试分别通过 `docker compose --profile dev run --rm dev pnpm typecheck`、`docker compose --profile dev run --rm dev pnpm test` 执行。运行期领域依赖、迁移 job、worker、release-build、多节点、network 和 observability profiles 尚未实现。Admin 目前没有认证和领域 API，不显示运营假数据。不得要求宿主机安装 Node/pnpm 才能开发/构建。CI 使用 Docker BuildKit 与 frozen lockfile，失败停止，不自动修改锁文件。

## 8. 构建与发布产物

web → HTML/JS/CSS/SW + 游戏资源 manifest；admin → 独立管理站点；server/worker → Node 可运行产物及镜像；mobile → 平台工程与签名包；desktop → 主进程/preload + web 静态产物 + 安装包。AI 母版、源代码映射和私密配置不作为默认静态部署内容。

Node 后端依赖最新受支持 LTS；Electron 内嵌 Node 跟随受支持 Electron 稳定版。构建环境台账记录工具、OS/CPU、版本与镜像 digest，容器包和服务器版本分别维护。具体依赖版本在初始化时按官方发布/支持政策核实，禁止用陈旧计划表替代即时核验。

CI 最小顺序：边界/类型/规则测试 → DB 集成 → 前端构建与资源校验 → 体积/manifest 检查 → 关键 E2E。原生平台构建另跑其 runner；不是每次修改文档都重建五端。正式版本执行弱网、资产故障、房间接管与目标设备检查。

发布供应链检查：使用 pnpm frozen lockfile 和 Docker BuildKit 生成可复现构建；CI 对依赖与最终镜像做漏洞扫描，生成 SBOM，扫描仓库/构建产物中的密钥，检查高风险许可证，并将扫描结果和镜像 digest 绑定到发布记录。生产只拉取已通过门禁的不可变镜像 digest，不在运行容器内安装依赖或执行构建。扫描例外须限范围、设到期时间并留审计，不能通过关闭整个扫描门禁处理误报。
