## 2. 配置表与版本

`system_config` 保存平台级业务配置，`game_config` 保存按游戏及档位组织的配置。工程包 `packages/config` 仍只提供 TS/ESLint 等构建配置，不承担业务配置存储；系统密钥使用环境或密钥管理，不放进可公开查询的配置表。

建议配置记录使用 `id、config_key、config_value、config_type、status、created_at、updated_at、deleted_at` 等基础字段；`game_config` 另有 `game_id、scope_type、game_tier_id`，明确区分游戏级与档位级配置。当前 SDD 将 system_config/game_config 设计为单条当前值，不额外保存 config version/effective version；修改前后值及原因由同事务 `admin_audit_event` 记录。Admin 配置修改人使用 `admin_audit_event.admin_user_id` 引用统一 `user.id` 并校验 ADMIN role_type；不新增 config_actor。

全局、游戏、档位仅允许显式声明的字段覆盖；校验通过后发布，支持预览、审计与回滚。客户端只取得白名单字段。数据库只保存每项配置的当前值；运行节点用 `updated_at`/缓存失效事件更新本地缓存，事务提交后通过 outbox 广播配置变更，定期从数据库核对，防止丢通知后永久使用旧配置。

牌局建立时生成已解析的不可变规则/档位快照；当局沿用该快照，配置修改不改变已经开局的计分和冻结上限。转账、首次赠币和返佣在业务记录/账务操作中保存实际采用的费率、比例及计算结果；配置修改有审计前后值，回滚配置只影响未来操作，不回写已完成流水。

| 配置集合 | 归属 | 内容 |
| --- | --- | --- |

| `wallet.initial_grant` | system_config | 新用户首次赠币默认 1000 枚、启用状态、领取资格与版本；沿用赠币默认 5 倍流水 |
| `wallet.transfer` | system_config | `feeBps=500`、发送方额外支付、手续费向上取整、报价有效期默认 60 秒、单笔/每日限额 `null`、最低保留余额 `0` |
| `wallet.withdrawal` | system_config | 用户填写净到账额；提现手续费率默认 5%，费用向上取整到分，出款等待 72 小时，minCoins=1000 且按净到账金币等值校验整数倍 |
| `coin_market.platform_fee_rate_bps` | system_config | 平台支付通道市场成交费率，默认 2000 bps（20%）；仅从卖家应收扣除，创建成交时快照，修改只影响后续成交 |
| `coin_market.minimum_listing_coins` | system_config | 最低挂牌量，默认 1000 枚；仅限制新挂牌创建，变更不改写既有挂牌 |

| `referral.rewards` | system_config | 四级上级充值返点为 10%/8%/5%/3%；邀请链接有效期默认 2 年；邀请注册奖励如启用，其金额与资格另行配置，规则未定义前关闭 |

所有玩法均由 `game_config` 显式配置开关和启用后的计分参数；开关关闭时不进入牌局比较或结算，开关开启时按该局冻结的配置快照结算。首版可使用报告中的 classic-v1 作为初始配置，但具体玩法开关由 Admin 配置；跨字段校验计分上限、奖励叠加与冻结需求，非法配置拒绝发布。

## 3. 金币转账与赠币

金币采用整数最小单位和整型运算，费率用基点表达，5% 为 500 bps。配置不设单笔和每日业务额度，允许余额转出后为零；冻结金币不可转出，仍遵守 `balance >= frozen >= 0`。接口参数有类型和整数存储范围，API 速率限制只限制请求频率，不伪装为金币业务限额。

手续费已确定由发送方额外支付：转 100，发送方扣 105、收款方加 100、平台手续费账户加 5。可用金币须覆盖本金与手续费；无最低保留余额不代表可以欠手续费。按最小单位向上取整，公式为 `ceil(金币本金×500/10000)`；例如转 101 枚，5.05 枚手续费向上取整为 6 枚。

客户端先取得含手续费、到账金额、总扣款、费率快照和有效期的转账预览，再确认提交。配置已变更时要求重新确认，不能静默改变扣款。实际转账在同一事务内校验可用余额，以一个 `asset_operation` 写双方及平台手续费分录和 outbox；所有账户按固定 ID 顺序加锁。同一幂等键只执行一次，保存金额、费率、收费方式和舍入结果用于审计。提现按用户期望净到账金额报价；默认提现费率 5%，例如净到账 100 元则额外收费 5 元、占款 105 元（默认比例相当于 1050 金币）。费用向上取整到分；最低提现门槛按净到账额的金币等值校验。

首次访问没有设备凭证时自动创建 user/device/session，并在注册 workflow 中调用新用户赠币用例。赠币默认 1000 枚，从全局配置读取；按默认赠币流水倍数 5 倍产生 5000 枚有效下注流水要求。赠币资格为每个 user 账号一次，不增加设备/IP 级额外限领；注册请求及 wallet grant 使用稳定幂等键，重试、设备登录、刷新、绑定邮箱/手机、换设备或二维码恢复均不得再次赠送。账号与赠币采用同一受控事务或可幂等恢复流程。该规则只保证每个账号领取一次，不承诺识别同一自然人跨账号重复注册。

## 4. 同表用户与常量化角色

`user` 是全平台所有账号的唯一身份主表；此前文档中的玩家 `accounts` 统一改称 `user`。邮箱、电话、用户名、密码凭证及 Admin 权限均在 `user`；设备及当前设备凭证保存在 `device`，恢复二维码凭证历史保存在 `recovery_credential`，钱包和关系实体按需引用同一个 `user.id`，会话只在 Redis。不另建代理或 Admin 身份表。Admin 通过 role_type ADMIN 位及权限码 JSON 区分，仍使用独立 Admin JWT audience/路由授权流程；代理角色不会获得后台权限。

邀请人是关系中的行为角色，所有正常用户均有邀请资格，不需要额外 INVITER 位；用户成为代理不会丢失玩家身份。SDD 当前采用常量位集合 `PLAYER=1、AGENT=2、ADMIN=4、SYSTEM=8`，有效组合为 `PLAYER`、`PLAYER|AGENT`、`ADMIN`、`SYSTEM`。返佣模式仍由 `reward_type` 决定，业务代码不散落字面量，也不使用 role_type 判断返佣数额。客户端不能直接提交或修改 role_type。

在 `packages/contracts` 提供 `UserRoleFlag`、`ConfigScope`、`FeeChargeMode`、`RewardType` 等运行时常量及对应类型，服务端执行合法位校验；数据库约束与迁移使用同一常量版本。Admin 不建 Role 表：`user.permissions` 保存权限码 JSON，`admin_permission` 维护权限码到 HTTP 方法/路由路径的目录映射。

referral 领域负责资格、关系与充值返点计算；wallet 领域负责实际记账。`referral_reward_allocation` 按来源订单、收款人和层级保存奖励/跳过结果，并以唯一键防止重复返点；每条记录保留奖励时的上级链和比例快照，Admin 后续换绑不重算旧奖励。客损返点由代理线下结算，平台不生成相应记录。

奖励和返佣已确定属于首版范围；`reward_type` 默认 1 为平台充值返点，2 为代理客损模式。四个上级比例 10%/8%/5%/3%；充值成功按实际支付金额计提，并冻结余额 2 天。客损模式由代理线下掌握充值/提现并结算；平台不参与该模式的提现、客损计算或返点发放。直属至第四级上级可在平台内向客损用户供币，转账记录在普通资产操作中。详见 [最新返佣细化](./邀请归因返佣与数据规范.md) 和 [代理客损模式边界](./累计客损结算口径.md)。

## 5. 账号绑定、恢复与二维码

设备/JWT 快捷登录仍是入口，提款前满足已绑定邮箱、已绑定手机、已设置用户名+密码三选一；不要求所有新用户注册时先绑联系人。二维码恢复仍支持但不单独替代提款身份条件。邮箱和手机绑定均不发送验证码；联系方式冲突不自动合并账户/金币/关系。

用户名规范化并建立唯一键；手机号保存国家区号及规范格式，邮箱按明确规范处理；密码只存现代密码哈希，建议 Argon2id，参数根据部署实测固定。联系方式绑定本身不提供所有权验证；安全变更通过当前密码（如已设置）和 TOTP（如已启用）重新授权。密码重置挑战使用随机、限时、单次消费机制并有尝试频率控制；恢复后轮换会话，提供撤销设备入口。[OWASP 密码存储](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)、[OWASP 密码重置](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)

“带密码”的二维码实现为密码保护的独立恢复凭证，不把用户名密码明文放进二维码。建议生成随机恢复 secret，二维码承载版本、凭证 ID 及用专用导出密码加密的恢复载荷；使用经过审查的带认证加密及密码派生实现，不自制算法。服务端保存 secret 的验证摘要、有效期和撤销状态，不保存可明文还原的登录密码。具体密码派生、密文尺寸与扫码兼容性在原型验证后锁定。[OWASP 加密存储](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)

恢复流程：扫码/导入图片 → 输入二维码密码 → 本地解密 → HTTPS 提交恢复 secret → 服务端校验并签发/轮换设备凭证 → 撤销旧会话并记 `last_used_at`；二维码本身保持有效，可以重复使用，直到被新二维码替换、主动撤销或过期，默认有效期 2 年。若账号已启用 TOTP，恢复时仍必须输入当前 TOTP；二维码不得重置或关闭 TOTP。用户无法提供 TOTP 或对此有异议时，转客服 IM 申请人工处理，由有权限的 Admin 核验并审计。二维码可保存至本地，默认不上传公共资源 CDN；二维码图片生成属于确定性账号功能，不调用图像模型。每个账号只保留一份有效二维码；重新生成时旧二维码立即失效，旧记录保留为 REVOKED。客服人工核验步骤由客服运营方案决定。二维码密码丢失时使用已绑定邮箱/手机或用户名密码恢复；全部凭证遗失的人工恢复标准另行定义。

identity 的账号主档统一使用 `user`：邮箱、电话、用户名、密码摘要、TOTP 和 Admin 权限均在该表；`recovery_credential` 保存二维码凭证历史。`device` 同时保存设备摘要和该设备当前的认证凭证，不再拆 `device_credential`；轮换/撤销动作写入 `user_security_event`，旧凭证与当前摘要不匹配即拒绝。会话和刷新状态放 Redis，不另建 session 表。验证码挑战由短期 Redis 状态承载。邮件和短信各提供端口及开发 Stub，真实服务商未指定，生产不能以 Stub 返回验证成功。发送接口 HTTP，验证码验证与绑定经事务处理，成功后 Socket 通知其他有效会话。

客服使用平台内一对一 IM：HTTP 创建/列出会话及补拉历史，Socket.IO 发送/接收消息；消息先持久化 MySQL 再 ACK，断线依 message id 续拉。首版支持文本，以及每条消息一个图片或白名单附件；所有通过 `asset` 上传的客户端文件先在浏览器按 AES-128-CTR 分块加密并逐块 HMAC 认证，再经统一资产流程上传/校验/存储，消息只保存 `asset_id`，下载按会话参与权限鉴权后在客户端验证、解密和渲染。授权客服可查看会话附件，密钥服务按会话权限向客服浏览器临时公钥交付密钥并记录审计；客服附件自上传起保留 2 年。多文件拆成多条消息。Admin 客服通过 `user.permissions` 中的 support 权限查看队列、分派和回复，不另建客服账号表。聊天在线状态/输入中状态放 Redis，客服人工处理 TOTP 遗失必须关联会话，并同时产生账号安全事件与 Admin 审计。

邮箱和手机号绑定/换绑都不发送验证码。换绑分别要求输入当前完整邮箱或手机号，服务端规范化后与当前绑定值精确比较；手机界面同时提示旧号码末三位。已设密码的账号需输入当前密码，未设密码时依赖有效登录会话；启用 TOTP 时两类变更均需当前 TOTP。新旧值在一个事务中替换，旧值提交后立即允许其他账号复用；邮箱不写入 `email_verified_at`。事件只保留脱敏值，不留明文旧联系信息。

所有 user（玩家和 Admin）均可自愿启用或不启用 TOTP，不设强制启用策略。待绑定密钥短暂放 Redis，扫码后以有效验证码确认才加密存入 user；使用 RFC 6238 兼容 30 秒时间步、窄漂移窗口和已用时间步防重放。密钥只在服务端加密保存；提供可选备用恢复码的哈希，验证失败限速。实现遵循 [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238)。

## 6. 浏览器优先与卡通素材

首版验收对象是手机和 PC 浏览器：包含邮箱/手机绑定、凭证二维码、用户名密码、配置后台、邀请奖励与返佣，以及原有大厅/游戏/钱包。App 在浏览器业务稳定后封装同一构建产物；提前保留平台适配端口即可，不提前实现五套业务代码。

封装仍需原生安全存储、触摸/音频/方向适配、构建签名和升级验证；“最后封装”是实施顺序，不代表这些工作自动完成。容量与弱网验收属于浏览器上线阶段，不应推迟到 App 封装后。

AI 风格规范固定大厅为卡通，三层大厅和十三张场景协调配色、轮廓与光照。预算较宽松不等于无限额：先完成接口试制，记录单位合格素材的尝试次数和成本，再由 Admin 或内部工具配置月度生产预算；尚未给出硬上限，不擅自设定金额。延续项目 venv 与 GPT-6 主模型约束。

验收覆盖：配置热更新不改变进行中的牌局；5% 手续费按向上取整并使分录守恒；无业务限额且允许零余额；提现占款包含净额和手续费且 72 小时前不出款；默认 5 倍赠币流水；并发转账与冻结不透支；重复恢复不重复赠币；同一用户可同时拥有多种关系角色；返佣按历史关系快照执行且只记账一次；未绑定邮箱/手机不得作为账号凭证；二维码密码错误、过期、撤销均拒绝，尚未替换/撤销/过期的有效二维码允许重复恢复；账务追回可造成玩家资产负数，负数期间不能消费、转账、兑换或提现，同一资产后续入账先冲抵其负余额；浏览器业务通过后再验收各平台封装。
