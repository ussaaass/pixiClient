# 支付渠道、流水要求与直连归因

本文件记录最新用户决定。关于赠币资格、提现触发、邀请 IP 歧义的旧方案以本文件为准；下列接口/表为待实现设计。

## 1. 确认配置与模式

余额以人民币 CNY 计价，余额与金币比例从配置读取，默认 `1 元 : 10 金币`。购买/兑出价格结构由配置明确表达。USDT 充值首版为 TRON/TRC-20；USDT/CNY 汇率 provider 可替换，每日取样一次，当日样本用于之后新建订单并在 `order.extra` 锁定；取价失败时暂停新 USDT 订单。CoinMarketCap 可作为技术候选，须确认 CNY 支持与项目商业授权；CoinGecko 当前 API 条款禁止其 API 用于提供在线赌博的产品，不能直接接入本项目。1:10 不是 USDT 汇率。

`reward_type` 属于领取返点的上级用户。模式 1 按客户成功充值的**实际支付金额**计算平台充值返点，冻结余额 2 天；模式 2 为代理客损模式，代理在线下自行掌握充值/提现差额并结算，平台不计算或发放该类返点。同一充值来源按固定关系、模式和配置快照分配，重复支付回调不重复返点。

## 2. 支付方式与提供商

| 玩家支付方式 | 接入路径 |
| --- | --- |
| 支付宝、微信、银行卡转账、银联二维码、数字人民币 | 第三方代理支付公司提供的支付方式，不表示分别直连官方支付体系 |
| USDT | 自建链上充值监测与订单匹配 |

微信是支付方式，不增加微信登录或小程序体系。支付方法与支付提供商分别建模，使用常量 `PaymentMethod` 与 `PaymentProviderType`；一个代理商可能提供多个方法，同一方法也可路由多个代理商。Sina Pay 仅为用户说明的同类举例，不是已选定供应商。

多家代理商通过 `payment_provider`/`payment_channel` 分别注册 adapter；可用商户与支付方式按配置顺序展示，由用户选择，订单固定所选 channel，不在创建后切换。首期用 `MockHandler` 完成调用链和页面联调，并提供仅开发/测试可用的关联 Mock 页面：展示订单号、金额和当前状态，允许测试人员模拟支付成功、失败、超时及重复回调，验证幂等与订单状态变化。页面通过后端 MockHandler 触发模拟事件，不能由浏览器直接改订单或账本；该路由/handler 在生产构建及生产配置中禁用，不能伪造生产支付成功。银行卡等延迟确认方法不凭用户上传图片自动发金币，必须得到经过验证的支付结果或受审计的人工处理。商户是否同时提供出款服务仍需核实。[OWASP 支付网关接入](https://cheatsheetseries.owasp.org/cheatsheets/Third_Party_Payment_Gateway_Integration_Cheat_Sheet.html)

纯前端离线施工阶段，支付渠道目录的每个启用项可直接进入 Admin Mock 控制台；选择渠道后创建的 `LOCAL_DEMO` 订单保存渠道 ID、provider code/name 和支付方式的不可变快照。应用用例从支付渠道查询端口重新解析并校验渠道仍为启用状态，停用/不存在的渠道不能创建新测试单；同一 requestKey 换金额或渠道会拒绝。后续生产接入仍须由 Payment Order 用例在服务端解析当前可用渠道并锁定订单快照，前端传入的 channel ID 不构成授权或支付成功证明。本地场景仍只改变 Mock 订单状态，不履约、不写资产账本、不模拟 provider 签名。

## 3. USDT 自建充值

USDT 充值已确定使用 TRON/TRC-20。主网资产合约以 Tether 官方公布标识配置白名单，测试网与主网彻底分离，不仅按代币名称认账；记录 token 精度和地址规范化版本。[Tether 支持协议与接入资料](https://tether.to/en/supported-protocols/)

独立链监测任务持久化扫描位置、区块/交易定位、接收地址和金额，按配置确认到账；事件唯一性使用 chainId + txHash + 链特定事件位置，不能只用 txHash，因为一笔交易可能有多个转账事件。扫描重复、服务重启和补扫不重复发币；未达到规定确认条件的记录只显示待确认。

每个 USDT 订单随机分配一个独立 TRON 收款地址，地址绑定该订单且不重复分配。TronGrid 或自建索引用于发现 Transfer，关键到账通过固化链状态和合约执行成功结果确认；不能把广播成功或索引刚出现当最终成功。超时、迟到到账、错额及无法匹配都保留事件并转客服处理，不自动履约。扫描使用固定区块顺序和日志定位，保存/核对执行结果与合约/接收人/数量。[TRON 确认语义](https://developers.tron.network/docs/confirmation-semantics)、[TRON 钱包接入](https://developers.tron.network/docs/exchangewallet-integrate-with-the-tron-network)

FX 端口输出 `base=USDT、quote=CNY、rate、source、quoted_at、expires_at`，每日刷新一次，服务端创建订单时固定当日报价，使用精确十进制计算；`金币=实付USDT×锁定USDT/CNY汇率×每元金币数`，充值返点以订单锁定的商品人民币金额/实付人民币等值为基数。回调/补扫不读取今天的新汇率重算旧订单，不默认 USDT 永远精确等于 1 USD。

每日取价时刻和时区、provider、异常阈值由配置确定；当日取价失败时暂停新单。已创建订单按快照和独立地址匹配；迟到/错额交易进入人工客服处理，不按新汇率重算，不自动履约。

监测器只读取链数据，不加载转账私钥。地址管理/归集签名单独授予权限和运行环境；不要在 web、API 回调或普通 outbox worker 暴露私钥。首版“自建 USDT”明确为充值能力，不默认还包括 USDT 自动提现；出款渠道需要另行明确。

## 4. 统一金币与赠币流水要求

用户已修正此前的分桶建议：赠币和普通金币没有使用差别，同一钱包、同一房间和普通游戏结算，不区分推广房间或永久不可兑金币。赠送金币同时增加待完成的**游戏流水要求**；符合条件后这些金币也按普通兑换/提现流程处理。

保留不可变的赠送来源和流水要求事件用于审计，但来源记录不形成第二种玩家金币。流水要求是提现资格，不是钱包 frozen，不应扣减金币或阻止正常游戏。

建议记录：

```text
requirementGranted = 累计已增加流水要求
requirementCompleted = 累计有效游戏流水，按事件匹配未完成要求
requirementRemaining = 尚未完成流水要求（不得小于 0）
```

赠币要求由 `gift_grant` 保存赠送业务键、金额和倍数快照，默认倍数为 5；每个用户仅用 `turnover_state` 保存当前剩余总流水，不另建 requirement/completion event、allocation 或 state 映射表。赠币发放和成功牌局结算分别在同一资产事务中增加/扣减该汇总；新增流水要求按金币数×倍数向上取整到整枚金币。平台不生成客损事件。取消、未结算或补偿原局不凭客户端出牌完成流水。

用户已确定有效流水按已完成牌局的有效下注额计算：下注 500 金币，完成流水 500，无论输赢，赢得的金币不额外计流水；赠币要求默认 5 倍并可配置。取消/作废的无效下注不计。保存每局玩家的 wagerCoins 事实，不用游戏净输赢绝对值，也不用客户端拖牌或名义申请额代替。

十三张此前只有每水金币及最大赔付冻结；`round_player.wager_coins` 保存规则规定的有效下注额，不默认等于最大赔付冻结。每局成功结算时用该字段扣减用户 `turnover_state.remaining_coins`，与资产结算同事务；牌局唯一结算记录保证同一局不重复计流水。取消或纠错时由牌局恢复/补偿流程同步修正汇总。

仅使用赠币要求生效后的有效下注完成当时未完成要求，按时间顺序消耗，不结转超额流水。每局已结算有效下注额按 `game_config` 配置的倍数计入流水；充值、转账、兑换、提现、奖励释放和纯冻结行为不算游戏流水。

赠币只增加流水要求，不追踪来源，也不参与平台客损计算。客损模式的充值、提现和返佣差额由代理线下掌握和结算；平台只执行直属上级模式对应的资产入口限制，详见[代理客损模式边界](./累计客损结算口径.md)。

用户已确定流水未完成时禁止金币转出，不采用转账携带流水方案。转账提交事务检查 requirementRemaining=0，失败显示尚需完成的金额；允许接收转账，但收到普通转账不自动增加或清除赠币要求。禁止转出是流水资格门禁，不新增单笔/每日金额限制；手续费仍由发送方额外支付 5%。

## 5. 提现准入与整数倍

对平台支持的提现用户（直属上级为 `RECHARGE` 模式），提现前必须满足任一身份条件：已绑定邮箱、已绑定手机、已设置有效用户名与密码。邮箱/手机绑定不发送验证码；设备/JWT 登录本身不满足该条件。提现申请和审核放行再次检验，联系人/凭证发生撤销不能沿用旧页面状态。直属上级为 `LOSS` 模式的用户由代理线下结算，不进入平台提现流程。

平台支持的提现用户，其金币兑换/提现门槛由配置决定，默认 `minWithdrawalCoins=1000`。以金币表达的提款金额需为门槛的正整数倍，即 `coinsEquivalent >= minWithdrawalCoins` 且 `coinsEquivalent % minWithdrawalCoins == 0`。余额仍是唯一出款资产，不跳过金币到余额的兑换。

建议余额提现统一使用本次报价换算金币等值验证，包括返点余额；默认 1:10 时，1000 金币等值 100 元，可申请 100/200/300…元。比例采用精确分数，不合法的金额拒绝并给出下一合法金额，不用浮点误差判定。此为余额提款如何落实金币门槛的技术解释，若返点余额需要独立门槛需另定配置。

申请预览保存比例版本、金币等值、余额金额、费用和有效期；审核不按新配置偷偷改原金额。金币兑余额和提现都检查流水剩余为 0，避免通过先兑换再提现绕过要求。余额返点冻结到期与客户流水清零是两项独立条件。

平台余额提现审核只处理平台余额出款资格、占款和外部出款，不触发客损计算或客损返点。客损模式用户不创建平台提现申请；代理线下办理客户提现与客损返点。平台充值返点仅由金币购买成功订单触发，与提现审核无关。

## 6. 直连邀请归因

访问网站后调用独立 HTTPS 直连接口（DNS 不经 CF），写 Redis 临时 `IP摘要 → 最新有效邀请码`；App/浏览器登录阶段再次请求相同接口，用服务端实际观测到的同一 IP 查归因。**最后一次有效访问覆盖前一次**，而非要求玩家在共享 IP 多个候选中自行选人。无效邀请码不覆盖有效记录；过期后没有自动归因。

邀请链接默认有效 2 年。IP→邀请码归因记录用 Redis 原子写入并带 TTL；它不同于邀请链接有效期，TTL 从 `system_config` 读取独立配置值，实施时按完成跨站访问/登录归因所需的最短时长设置，不默认保留两年。真实账号上下级仍在 MySQL。[Redis TTL](https://redis.io/docs/latest/commands/expire/)

建议只在独立轻量入口暴露归因服务，不把主业务源站开放为同一个直连地址。接口用 TLS、固定允许来源及轻量请求限频；CORS 不是身份认证。邀请代码不是登录密码，IP 只用于按用户要求做归因。服务器不信任客户端 body/header 自报 IP，代理链若存在必须明确可信边界。

解析结果可换成短期签名 attributionTicket，客户端携 JWT 提交到 CF 保护下的绑定 API；或由直连接口验证 JWT 后调用同一绑定用例。两种实现均可，首版选一套，不额外要求玩家确认选择。票据固定 lookup 时读取的归因版本，后续新访问不篡改已经提交的绑定请求。

数据库事务校验初绑、自绑定、防环/层级、账号状态及既有关系，幂等写绑定及审计；已有上级永不被 IP 最新候选覆盖。Redis 与 MySQL 不假装有共同事务：数据库先持久化实际归因版本/操作结果，Redis 的清理/消费后续幂等完成。单一 IP 记录是否在一次绑定后删除还是在 TTL 内供多个账号使用尚待明确；无论哪种策略，多次登录同一用户都不重复绑定。

其余页面、API、游戏 Socket 与管理入口继续按既定 CF/大陆优化线路配置，只有归因入口直连。网站与 App 观察到 IP 不同可能无法关联，此时使用邀请码回退或维持未绑定；不能仅凭类似 IP 猜测上级。

## 7. 数据、目录与验收

配置归属：system_config 的 wallet.exchange 保存默认 1:10；wallet.initial_grant 默认 1000 枚；wallet.withdrawal 保存 feeBps=500、minCoins=1000、整数倍要求、身份/流水门禁和 72 小时等待；wallet.transfer 保存默认 feeBps=500 及向上取整；wallet.gift 默认流水倍数 5；identity.recovery_qr 与 referral.invite_link 的有效期默认 2 年；support.asset_retention 默认 2 年；referral.attribution 保存直连接口地址/IP→邀请码临时记录 TTL/归因规则；payments 保存支付商户/显示排序、每日 FX provider 与采样时间、USDT 尾数槽位和订单时限。game_config 的 tier/rules 保存每局 wagerCoins、玩法启用开关及玩法参数、有效下注/作废规则。API 凭证、钱包私钥及内部签名密钥不入公开配置，实际密钥仍只在受控服务端环境。

流水资格只新增 `turnover_state` 汇总；赠币要求在 `gift_grant`，下注事实在既有 `round_player.wager_coins`，不单建流水事件和分配表。支付实体以 SDD 单数表名为准：`payment_provider`、`payment_channel`、`chain_deposit_event`、`chain_scan_cursor`。全表保留 created_at/updated_at/deleted_at/status，状态非零且代码常量化。chain 事件/流水/审计不可软删除。

backend wallet 管理流水资格，payments 细分 providers 与 chain-deposits 适配，referral 管理归因/返点；workflows 协调游戏结算和提现审核。若直连归因独立部署，增加小型 apps/attribution 入口而不拆出新数据库；链监测可用专用 worker 入口，原型阶段不用空目录填满全部服务。

验收覆盖同 IP 最新有效邀请码获归因且不换绑旧关系；CF 主入口与直连服务边界明确；平台充值返点按实付金额且只由成功订单触发；客损模式用户不能创建平台充值/兑换/提现，当前祖先链上级供币正常记账且不触发充值返点；赠币增加流水要求；取消牌局不完成流水；新增赠币不误用历史超额流水；默认 1000 枚及其整数倍门槛正确；三选一身份有效；代理重复回调/链补扫不重复发金币；USDT 链及资产不匹配不认账；全部新状态拒绝 0。
