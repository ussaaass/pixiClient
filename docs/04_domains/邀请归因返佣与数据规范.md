# 邀请归因、返佣与数据规范

本文记录最新补充，覆盖之前“最多五个上级”“返佣触发时机尚未指定”等旧建议。当前仅设计，用户已确认充值购买金币、返点入余额、金币兑换余额后提现，详见 [双资产充值兑换与提现](./双资产充值兑换与提现.md)。

## 1. 邀请链接与 IP 归因

邀请人发放含邀请码的链接；网站调用独立不经 CF 的接口，在 Redis 带 TTL 保存实际观测 IP 与最新有效邀请码。App/浏览器登录再请求该接口，同 IP 尝试首次绑定；最后一次有效访问覆盖前一次，其余页面/API/Socket 保持原有 CF 路径。详见 [直连归因方案](./支付渠道流水要求与直连归因.md)。

Redis 临时键保存 IP 摘要、邀请码、归因版本和 TTL，不为每次网站访问写 MySQL；实际绑定结果与所用版本进入关系审计。IP 统一表达、可用服务端密钥摘要等值匹配，只信任明确代理边界，不接受客户端自报 IP。

登录成功后：查询未过期候选 → 校验邀请代码/邀请人有效 → 检查用户尚无上级 → 在关系写入事务内检查自绑定、循环、层级和期望版本 → 建立绑定并记录归因依据。已有上级的账号不因再次访问链接或换 IP 被换绑；换绑继续只允许 Admin。候选状态与绑定结果需要可查询，重复登录不重复产生关系或奖励。

同 IP 采用最新有效邀请码，不增加玩家选择归属步骤。IP 是归因依据，不是认证凭证；已有上级不会被新的 IP 记录换绑。邀请链接/代码默认有效 2 年；IP→邀请码临时记录另有独立 Redis TTL，避免把 IP 归因数据也保留两年。不同 IP 不自动认领，相同临时记录能否供多个新账号使用及回退邀请码的具体流程在 referral 模块实现前确认。

## 2. reward_type 与计数修正

`user.reward_type` 是非空常量字段：`RewardType.RECHARGE_REBATE=1`（默认）、`RewardType.CUSTOMER_LOSS_REBATE=2`。客户端不可自行提交 reward_type 修改返佣方式，受控配置/管理用例记录修改审计；修改仅对新事件生效，不重算已入账奖励。

用户最新说明“加上被邀请人本人共五级”：本人为第 1 级，最多四个上级，数据库关系边数最多 4；此前直属上级为第 1 级且最多五条边的草案作废。当前使用固定四级祖先列，不建闭包表；应用层层级计数从直属上级 1 开始，避免与“本人第 1 级”的产品口径混淆。

物理字段使用 `parent_1_user_id` 至 `parent_4_user_id` 的连续命名，避免各层使用不规则字段名。`referral_binding` 同时有 `parent_1_benefit_cents` 至 `parent_4_benefit_cents`，分别累计当前绑定期间由该用户实际给对应层上级带来的已发充值返点，按层索引便于代理报表筛选和求和。它们是读取投影，奖励明细仍以 `referral_reward_allocation` 为账本事实；换绑重建新关系链时新关系累计归零，旧关系历史按 allocation 的 ancestry snapshot 查。

用户已确认：10% 为直属上级，层次升高依次为 8%、5%、3%。配置保存 `1000、800、500、300` bps，映射上级距离 depth=1/2/3/4；包括本人即五级。本人为来源客户，不占用这些上级比例，不添加第五个比例；独立自返和邀请注册奖励不能因此被推断为已定义。

`reward_type` 属于领取返点的上级。`RECHARGE_REBATE` 模式只对符合条件的金币购买实付金额计算平台充值返点。`CUSTOMER_LOSS_REBATE` 模式下，代理在线下自行结算客户充值与提现差额；平台不计算或发放客损返点。平台的 `referral_reward_allocation` 只保存平台实际发放的充值返点。

## 3. 已确认触发与冻结期

| 奖励模式 | 触发事件 | 入账与限制 |
| --- | --- | --- |
| 充值返点（1） | 充值成功 | 入账为冻结奖励，冻结 2 天后可提现 |
| 客损模式（2） | 代理线下自行结算 | 平台不参与客损计算、入账或冻结 |

充值奖励“即时可见、冻结 2 天”：成功记账后可看到余额奖励，但释放前不可提现，不增加游戏金币。按支付渠道验证的成功订单入账，不能依前端跳转判断成功。充值订单与 reward allocation 用稳定唯一业务键防止回调重放重复返点。Admin 换绑不修改既有奖励，allocation 保存订单成功时的关系快照。

客损模式下，直属上级为 `LOSS` 的用户不能使用平台金币购买、金币兑余额或平台余额提现入口；其当前邀请链中的直属至第四级上级均可向其转入金币。平台只记录该笔普通金币资产转账及供币操作者，不将它认作充值，不产生充值返点。代理与客户线下掌握充值/提现及返点结算；平台不保存客损高位或返点数据。详见 [代理客损模式边界](./累计客损结算口径.md)。

## 4. 冻结奖励实现

奖励冻结复用 SDD 的 `asset_hold`：allocation 通过 `asset_hold_id` 指向奖励占款，hold 保存金额、剩余额和 `expires_at`；创建、部分释放、最终释放或消耗都在同一事务更新 hold、账户 `frozen_amount`，并写带 `asset_hold_id` 的不可变 `asset_entry`。不为奖励冻结另建表。

worker 扫描到期的奖励 hold，在数据库事务内幂等释放并写 outbox；多 worker、重启和重复执行只释放一次。离线用户无需登录也能释放。释放不能早于 `expires_at`；提现检查在事务内确认到期 hold 已释放或从可用余额排除，不能只靠 UI 倒计时。

提现记录保存余额版本和占款凭证，拒绝/确认失败释放，成功不可重复扣。余额 CNY、充值方式及 TRON 已明确，实际渠道凭证未接入，Stub 不伪造成功。

## 5. 充值与提现改变原有资产范围

充值购买金币，返点入人民币余额，金币按配置默认 1:10 兑换后提现。代理支付与 TRON USDT 充值路径已明确，赠币统一使用、以流水要求限制提款，具体见最新支付与流水文档。

正式规划 payments 领域、余额账本、兑换、withdrawal 用例及奖励冻结释放；具体见双资产方案。金币转账 5% 不自动套用到充值、兑换和提现。

## 6. 全表基础字段与状态常量

所有业务、关系、配置、队列持久化、流水、审计及迁移历史表必须包含以下字段；不用带豁免的“默认只给主表”约定：

| 字段 | 规划 |
| --- | --- |
| `id` | 每张表独立主键，BIGINT UNSIGNED |
| `created_at` | 非空 DATETIME，UTC 创建时间；按最新命名规范 |
| `updated_at` | 非空 DATETIME，创建时与 created_at 相同，合法变更时更新 |
| `deleted_at` | 可空 DATETIME，未删除为 NULL |
| `status` | 非空正整数，由该表的状态常量定义合法值 |

所有其他状态字段也不允许 0，包括 `review_status、payment_status、reward_status` 等；不能使用 0 表示未知、禁用或待处理。状态常量归属具体领域；奖励冻结通过 `asset_hold` 状态与到期时间表达，不另设 `RewardLockStatus`。role_type/reward_type、错误码与状态分别定义，不能复用一套数字枚举混淆语义。

`deleted_at` 存在不代表所有数据可删除：金币分录、已完成支付/奖励、审计记录等不可改写或软删除，字段保留 NULL，纠错通过新补偿事件/分录实现；不可变分录的 updated_at 固定为创建时间。审计数据保留规则独立管理，查询不能默认过滤到隐藏已撤销业务痕迹。

幂等键、原始业务 ID 和财务流水唯一性不会因软删除释放。其他可复用唯一值必须按明确策略设计，不能仅在唯一键中追加可空 deleted_at。迁移历史若由工具自动创建，也需配置/适配以满足基础字段；不兼容的迁移工具不能无说明地作为例外。数据库检查约束、DTO 校验和状态转换常量共同保证非零合法值，禁止代码到处写 status=1/2 的裸数字。

全表 snake_case、表/字段注释、引用 abc_id 及同表多角色关联模型，具体见 [最新 Sequelize 数据库规范](../05_data/数据库设计规范与Sequelize方案.md)，旧祖先/后代前缀字段草案不再直接使用。

## 7. 结构与验收

referral 管理 IP 归因、树与返点计算；identity 管理登录和 reward_type 授权变更；wallet 管理双资产、兑换、冻结/释放/补偿；payments 管理支付渠道与对账；configuration 发布比例和归因策略；worker 执行到期释放。渠道未配置的 Stub 不伪造成功事件。

验收覆盖：同 IP 最新有效邀请码自动初绑且不覆盖已有关系；IP 来源不可任意伪造；本人计入五级、禁止第五个上级；模式按收款上级且默认 1；审核通过事件只返一次；2 天/1 天奖励不提前释放；流水门禁及整数倍提款正确；全表基础字段齐全，所有状态拒绝 0 并常量化。

### 邀请链接 API 与本地开发边界

已登录用户可读取或签发自己的邀请链接；邀请码映射生产 `user.invite_code`，有效期映射 `user.invite_code_expires_at`，默认两年。有效期内重复签发返回同一链接，过期后才重新签发。链接中的邀请码仅用于进入邀请归因流程，客户端不得提交或修改上级关系。

浏览器开发服务器将邀请码与过期时间保存在 IndexedDB 的既有 `users` 行，生成 `/?inviteCode=...` 链接供复制。页面启动时调用共享 DTO 的公开候选接口；开发适配器使用固定的本机模拟来源键（不是 IP 地址），以 `system_config:referral.attribution.candidate_ttl_seconds` 暂存最后一个有效邀请码。缺省/非法值回退到 900 秒开发默认值，允许范围 60–86400 秒。首次创建设备账号时，开发服务端消费未过期候选并写入独立 `referral_bindings` 本地 store，按邀请人的既有祖先链复制最多四级；已有设备重登不会改写关系。该实现只验证客户端到 Browser API 的协议与本地流程，不模拟真实 IP、Redis 或 MySQL 事务，也不代表生产绑定已完成。生产仍由不经 CF 的归因服务观察真实 IP、使用同一 system_config TTL 写 Redis 候选，并在注册/登录事务中完成关系初绑；客户端不能传 parent ID。
