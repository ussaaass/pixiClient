# 系统账户与资产记账设计

## 1. 已确认业务与接入含义

系统账户是内部资产流转的来源和归宿。商品“2000 金币”售价 200 元：用户支付成功，系统账户余额增加 `200 元 - 支付通道手续费`，系统账户金币减少 2000，用户金币增加 2000。用户返点及兑换余额也由系统账户支出；金币回收、兑换和平台转账手续费归系统账户。

“商户 API”只是实际代理支付公司的技术接入资料：订单创建/查询、回调验签、商户号/渠道参数、退款/对账以及可用的出款能力。支付宝、微信、银行卡、银联二维码、数字人民币是该公司提供的方法，不代表分别直连官方接口，也未指定新浪支付为最终商户。接入参数不是另一项玩法规则。

## 2. 账户与数据

user 表统一保存所有账号；role_type 常量位中 SYSTEM 标识唯一系统账户、ADMIN 标识后台管理员。资产账户的 account_type 仅区分 PLAYER/SYSTEM 账务账户，由 user.role_type 推导；ADMIN 不创建游戏资产账户。系统身份禁止玩家登录、邀请绑定及普通转账操作，业务请求不能指定 system user_id 代替自己。管理权限字段保存在同一 user 行，Admin 操作由审计记录追踪，不另建 admin_user 表。

asset_account 保存 user_id、asset_type、currency、amount、frozen_amount、version；系统与玩家每种资产各一个账户。金币用整数单位，人民币余额用分；amount 与 delta 使用有符号精确整数，系统金币发行余额允许为负，玩家金币和人民币余额也可因审计追回/冲正而为负，系统人民币不允许为负；ID 仍使用 BIGINT UNSIGNED。AssetType.COIN=1/CNY_BALANCE=2 等由代码常量定义，非人民币币种本阶段不新建可提现用户余额。唯一键按 user_id/asset_type/currency，全部表满足 id BIGINT UNSIGNED 与三个 DATETIME 及注释规范。

asset_entry 每条保存 asset_account_id、asset_operation_id、有符号 delta、记账后金额/版本和事件信息；amount 与 frozen_amount 不直接混为财务流水。asset_operation 的幂等键与业务摘要固定，不用不同随机 ID 重复履约。外部支付/出款标识保存为 external_transaction_key，不误称其他内部表的 id。

系统账户是唯一系统业务主体，不等于仅有两行全用途分录。支付入账、通道费用、返点、赠币、兑换和外部出款按 operation_type 拆明细，不能只记一个无法解释的净差。资产锁、待结算渠道资金与返点承诺分别保存原因和占用，不把系统账户可用余额算成总额。

## 3. 充值例子与费用

以通道费 F 元表达，手续费尚未指定实际费率，不能把金币玩家转账 5% 当作支付通道费。

| 对象 | 金币变动 | 人民币余额变动 |
| --- | ---: | ---: |
| 系统账户 | -2000 | +(200-F) |
| 购买用户 | +2000 | 0 |

external_settlement 固定充值订单、渠道、实付 200、费用 F、净额 200-F、币种和通道结算状态。充值返点仍以**实际支付 200**为基数，不因平台收到净额而改成 200-F；各上级按 reward_type 与对应比例分别由系统余额转入上级冻结余额，保存同一资金操作引用。

渠道费未返回时不能伪装成已知 F：保留应计/待核实费用及差异状态，按商户计费配置估计并在正式对账后追加差额分录。用户支付成功不一定表示通道已经向平台结算，未结算净额使用明确系统资金 hold，不作为即时可用出款资金；通道查询/正式结果是依据，不用截图或前端跳转。

USDT 充值实际链金额按锁定 USDT/CNY 报价折算，用户商品实付等值、费用和净入账分开。真实 USDT 收款不等于银行账户立即增加 CNY：外部资产/换汇明细保存原 USDT 持仓、计价及可结算状态；系统人民币账本是业务计价，实际人民币出款仍需对应可用资金，不能靠标价即假装兑换完毕。

## 4. 内部业务分录

| 业务 | 金币分录 | 余额分录/限制 |
| --- | --- | --- |
| 赠送 1000 金币 | 系统 -1000，用户 +1000 | 无人民币转账；另增有效下注流水要求 |
| 客户兑换 1000 金币，默认比例 | 用户 -1000，系统 +1000 | 系统 -100 元，用户 +100 元 |
| 发放上级返点 20 元 | 无 | 系统 -20，用户 +20 且创建对应冻结；1/2 天由奖励类型决定 |
| 玩家转账 100 金币 | 发送者 -105，接收者 +100，系统 +5 | 无人民币分录；发送者流水须已完成 |
| 冻结奖励到期 | 无 | 只释放用户冻结 hold，不再次给用户增加 20 元，也不再次扣系统 |
| 四人游戏结算 | 用户间按得分转移，净合计 0 | 不给系统凭空加金币；如配置服务费须单列系统收入 |

内部每种资产分录合计为 0。跨资产兑换分资产各自守恒，不将 1000 金币与 100 元直接相加。系统只承担平台来源/回收业务，不成为每个玩家对玩家赢家输家的额外对手。

## 5. 提现与外部边界

兑换时系统余额已转到用户余额。平台支持的余额提现：占用用户未冻结余额 → 审核通过 → 出款服务/人工审核流程 → 成功扣用户余额。客损模式客户的提现及返点由代理线下结算，不进入此平台提现流程。不能在实际出款时又扣一次系统内部余额，否则同一兑换提现链会双扣。

外部资金真正离开平台时，external_settlement 记录收款渠道/对象、实际转出、手续费和结果，并与用户扣款关联。外部支付净流入和出款净流出改变平台内部余额总额，因此“所有操作的内部分录都必须合计 0”只适用于内部转移，不适用于带外部资金的充值/出款。

可核对：

```text
本期内部人民币余额总额变化
  = 外部入金人民币净额 - 外部出金及已记费用 + 受审计期初/补偿调整
系统及玩家金币账本合计
  = 固定期初账本合计（内部发行/回收均成对平衡）
若全部账户期初为 0：玩家流通金币合计 = -系统金币发行余额
```

具体外部币种按原币分别对账；未结算通道资金和 USDT 持仓不能无条件等同银行 CNY。多种外部资产的估值由固定版本保留，不以每天汇率波动改写用户历史分录。

## 6. 系统库存、余额与容量

用户已确认：系统金币发行余额允许为负。系统金币从 0 开始时，出售或赠送 2000 金币记为系统 -2000、玩家 +2000；金币回收增加系统金币发行余额，减少玩家流通量。不要求 Admin 先补正库存，发币仍须有合法业务、幂等键与审计，不允许直接 UPDATE 绕过账本。系统人民币余额禁止仅凭配置增发，增资/补偿须明确实际来源及审计。

玩家金币和玩家人民币余额可因已审计的返点追回、冲正或补偿调整而为负；负余额不构成可用资产，常规消费、下注、转账、兑换和提现不得使余额进一步透支。同一资产的后续合法入账先抵扣该资产负数，再形成正的可用金额。所有账户满足 `frozen_amount >= 0` 且 `frozen_amount <= max(amount, 0)`。系统金币发行账户 `frozen_amount=0`，允许 `amount` 为负，不执行正库存门槛，但必须检查有符号整数范围；系统人民币仍不得为负。例子若 F=2 元，充值净入系统 198 元，但 2000 金币按默认比例可兑换 200 元；若还需返点，系统更需要已有人民币资金覆盖差额。负金币发行余额不增加可用人民币；系统人民币余额不足时保持待处理且不伪装成功。

同一系统资产账户会被充值、赠币、手续费、兑换和返点共享，单行写锁可能成为并发瓶颈。首版仍按用户要求一个逻辑系统账户，所有账户按固定 id/资产次序锁，事务短且不做外部调用；压测记录系统账户锁等待。若需要账务分片，必须保持同一逻辑账户及可核对聚合，不在本阶段偷偷增加多个互不一致的系统账户。

## 7. ORM、幂等与验证

所有资金用例经 Sequelize UnitOfWork，asset_account/entry/hold、订单、奖励和 outbox 同事务；外部接口在事务之外。系统金币无须预占正库存；支付成功后的履约须幂等，账户状态、整数范围或事务异常导致暂无法发币时保持订单可恢复状态，不能抹掉已收到款项。

验收：200 元订单按 200-F 入系统、用户仅加 2000 金币；通道费与返点基数分别保留；重复回调不重复记账；返点/兑换/赠币从系统扣相应资产；提现不双扣系统；冻结释放不二次入账；内部转账分资产守恒；外部收支对账一致；系统金币从 0 到 -2000 合法；已审计追回可使玩家 COIN/CNY 为负；常规扣款不得扩大玩家负余额、系统 CNY 不可透支；所有资金分录和注释可追溯。
