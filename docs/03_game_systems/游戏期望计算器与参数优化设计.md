# 游戏期望计算器与参数优化设计

阶段：平台级设计基线，供后台与游戏数学模块评审。目标是在运营人员保存游戏/难度配置前，展示该配置对概率、返还和玩家结果的可解释影响，并由受约束的优化器生成候选参数，降低手工改错概率。

## 1. 设计目标与边界

期望计算器按 `game_key + difficulty_key + game_config版本 + math_model版本` 工作；获授权时可增加 `agent_domain_id` 作为计算 scope。计算器不接受真实下注，不调用钱包、支付、资产流水、生产随机数或正式牌局 handler；模拟的样本、玩家和奖池都是内存中的虚拟对象，不创建游戏局、订单或任何数据库记录。管理员发布平台配置写 `game_config`；代理只能发布经过全局边界校验的域级 override，并写不可变审计记录。“不落库”指计算过程和模拟轮次不写业务数据库。详见[代理域设计](../04_domains/代理域设计.md)。

计算器不是一个平台通用的“赢率”数字。不同游戏输出不同指标：随机派奖类报告 RTP/命中率/盈利率；十三张等对战类报告给定对手策略分布下的胜率、平局率和期望净分；外部开奖类以真实开奖结果空间计算概率，不模拟或操纵外部开奖源。

工具不得以近期玩家输赢、充值/提现、资产、设备、IP、邀请关系或行为画像调整个体概率，也不得根据实盘偏差自动改生产赔率。优化只针对管理员当前编辑的候选配置和明确给出的目标/约束，输出建议，由人复核并发布。

## 2. 指标定义

### 2.1 随机派奖游戏

对单次投入 `B`，结果 `i` 出现概率为 `p_i`，玩家获得的总返还（含退回本金）为 `G_i`：

```text
理论 RTP         = Σ(p_i × G_i) / B
玩家期望净值     = Σ[p_i × (G_i - B)]
平台理论毛差额   = B - Σ(p_i × G_i)   // 不含渠道费、奖励、返佣等成本
命中率           = P(符合已定义的“命中”条件)
净盈利率         = P(G_i > B)
回本率           = P(G_i = B) 或依游戏规则定义的 P(G_i ≥ B)
```

UI 必须将“有派奖”“收回本金”“本局净盈利”分开显示。免费局、累积奖池、连锁状态、特殊模式都必须进入完整模型，不能只用基础局数据冒充总 RTP。若付费局触发一个或多个免费轮，RTP 分子累计付费局及其奖励链的全部返还，分母只计实际扣除的付费投入；免费轮不得伪装成新增付费样本。翻倍轮按该游戏明确的派奖规则计入返还，不能误计为新增投入。

游戏支持按概率或积分触发免费轮/翻倍轮时，模型和报告还应分开展示触发方式及配置版本、触发率、每个付费局的平均免费轮数、免费轮贡献返还、翻倍轮触发率及其返还贡献。按积分触发时，说明积分如何获得/消耗及每次模拟的积分初始条件；概率与积分机制同时存在时，应覆盖交互组合。自动模拟单位仍是一局付费开局及其完整奖励链，额外统计的免费轮次数不应被当作额外付费局数。配置、记账、恢复和 handler/math 契约详见[奖励轮与派奖倍数机制 SDD](./奖励轮与派奖倍数机制SDD.md)。

### 2.2 对战类游戏

十三张等玩家对战不具备单人 Slot 式固定 RTP。结果依赖规则、策略和对手构成。报告必须列出模拟策略/机器人版本：

```text
胜率             = P(本方结果优于目标对手/目标桌)
平局率           = P(本方结果相同)
净分为正概率     = P(本方按完整结算规则的总净分 > 0)
每局期望净分     = E(本方净结算分)
每局期望金币变化 = E(本方实际金币变动)
```

玩家对玩家桌的分数转移与系统手续费要分开。改变陪玩机器人策略档会改变对手分布，报告不得混为同一胜率。应分别展示单个对手、典型混合桌和配置允许的机器人构成。

### 2.3 概率活动/共享奖池

每个活动状态单独给出基础配置与活动配置的概率分布、RTP/派奖、池资金消耗和持续期估算。概率权重必须完整归一化，并锁定 `odds_profile_version`。奖池额外派奖和基础游戏派奖分开展示。详见[陪玩机器人与概率模型设计](./陪玩机器人与概率模型设计.md)及[平台事件与广播系统设计](./平台事件与广播系统设计.md)。

## 3. 结果来源与计算精度

`GameMathModel` 由每个游戏模块实现；平台只负责调度、报告展示和候选参数工作流。

```ts
interface GameMathModel<TConfig, TScenario, TReport> {
  validateConfig(config: TConfig): ValidationIssue[];
  exact?(config: TConfig, scenario: TScenario): TReport | null;
  simulate(input: {
    config: TConfig;
    scenario: TScenario;
    runs: number;
    seed: string;
  }): Promise<TReport>;
  optimize?(input: OptimizerInput<TConfig, TScenario>): Promise<OptimizerProposal<TConfig>>;
}
```

要求：

- 赔率、概率和奖表使用整数权重或精确有理数；资产与返奖展示按规则约定的最小单位计算，不以 JS 浮点数承担账务运算。
- 模型必须调用与正式游戏相同版本的纯规则/判奖代码，但运行在隔离的 simulation adapter 中；禁止调用任何生产钱包、随机源、DB repository 或外部支付/开奖接口。
- 模型输出 `game_key`、`difficulty_key`、配置摘要、配置版本、数学模型版本、玩法规则版本、随机种子、样本数、生成时间、指标定义和警告。
- 确定性模型优先精确枚举；无法精确计算的部分用 Monte Carlo 估计，并给出估计量、标准误/置信区间和适用假设。统计区间的解释与适用前提应在帮助文案中说明；NIST 的区间估计资料可作统计方法参考。[NIST：置信区间方法](https://www.itl.nist.gov/div898/handbook/prc/section2/prc221.htm)
- 不把客户端输入的配置直接执行为代码；每个游戏使用版本化 schema 和白名单参数路径校验，拒绝未知字段、越界参数和不支持的组合。

## 4. 1000 轮快速模拟

管理端每次“试算”默认执行 1000 个独立模拟单位，作为交互式快速检查。不同游戏的一个模拟单位必须由模块明确定义：Slot 是一次完整 spin（包括该 spin 触发的免费局链）；十三张是一整桌完整发牌与三家比较；捕鱼是有明确炮数/会话长度的 scenario；“3快”是一次完整下注类型结算，不生成或预测未来外部开奖号码。

结果面板必须显示下列分布和统计值：

- `1000 次快速模拟`，以及每一轮的定义、随机种子和模型版本。
- **结果分布**：按游戏奖级/结果类别统计次数、占比、单次返还和累计返还；再给出每局返还/净输赢的分布图或分桶表。分桶边界由该游戏数学模型定义并随报告展示，不能为了美化结果动态改桶。
- **模拟实际 RTP**：`模拟全部总返还 ÷ 模拟全部总投注`，同时显示总投注、总返还、净差额和样本局数。该值是这批模拟样本的观测 RTP，不等于理论 RTP；若各轮下注额不同，按总金额比值计算，不能简单平均每轮 RTP。
- **轮空率**：未获得任何派奖的模拟局数占比，定义为 `G_i = 0`；如果具体游戏把返还本金也算“命中”，仍须把轮空单独按“无任何派奖”口径报告，并将回本率另列。
- **大奖率**：达到该游戏已配置“大奖”门槛的局数占比，显示大奖定义/奖级阈值、次数和样本比例；奖池类游戏同时显示大奖总额与耗池额。未配置大奖门槛时显示“不适用”，不能由通用平台擅自猜阈值。
- **方差与波动**：逐局返还和逐局净输赢分别给出样本均值、样本方差、标准差；对不同投注额场景还提供单位投注归一化结果。长尾金额另显示中位数、P95/P99、最大值和奖池耗尽比例（适用于该模型时）。
- 各比例/均值给出适用的 95% 置信区间和标准误；方差等统计量说明采用的估计口径。轮空/大奖概率的区间应使用适合二项比例的区间算法，不能在小样本下只依赖正态近似。
- 理论/精确值与模拟估计并列；差异超出阈值时显示“模型或样本差异需调查”，不能静默接受。
- 对低概率/高额奖项显示“该样本量无法可靠估计”的醒目提示。若某事件真实概率远低于 1/1000，1000 次样本常常一次也观测不到，不能据此说概率为零或声称验证通过。
- 一键扩大样本只增加临时计算，不改变模拟的无副作用属性；大样本任务可异步放入独立计算队列。

大数定律说明样本均值在满足相应假设时随样本增大趋近理论期望，不保证任一有限样本的结果接近理论值。1000 轮是快速预览，不是“长期结果保证”或稀有事件认证。复杂/长尾玩法上线前应使用精确枚举、重要性抽样/分层方法或更大样本验证，并记录方法和区间；报告必须避免把模拟期望包装为玩家实际收益承诺。

## 5. 参数自动优化器

### 5.1 操作流程

```mermaid
flowchart LR
  A[选择游戏与难度] --> B[载入当前配置草稿]
  B --> C[选择目标指标与硬约束]
  C --> D[白名单参数范围搜索]
  D --> E[候选参数 + 数学报告 + 风险提示]
  E --> F[1000轮快速模拟/对照]
  F --> G[管理员复核并提交发布]
  G --> H[写入配置版本与审计记录]
```

优化器只调整当前游戏 `math_model` 标记为可优化的参数，例如整数奖项权重、奖项金额档位、鱼种公开倍率/权重或活动池上限。它不能编辑任意 JSON 任意字段，更不能改认证、资产、用户或安全配置。

每个优化任务要求运营填写目标和边界，例如“RTP 目标范围”“最大单局奖额”“奖金池最大负债”“命中率区间”“体验波动/方差上限”。硬约束优先于目标函数。系统返回最多若干个候选解，逐项展示相对当前值的改动、指标前后对比、限制原因和未满足目标；若无可行方案，返回无解及冲突约束，不自行放宽界限。

对“体验起伏”可以比较方差、盈亏序列分布、空转间隔分布等统计特征，但不能把“刺激用户继续下注/挽回损失”设为目标函数，不能按某个用户调整开奖结果。用户已确认的厅级活动仍按公开、版本化、全厅统一规则处理；计算器只验证其概率和池资金结果。

### 5.2 安全发布

```text
DRAFT → VALIDATED → SIMULATED → PROPOSED → REVIEWED → PUBLISHED
```

- DRAFT/VALIDATED/SIMULATED/PROPOSED 等是工作流状态，不对应持久化草稿表；编辑候选保留在当前页面状态，试算/优化任务只使用临时 worker 与带 TTL 的 Redis 任务状态，不写模拟轮次或结果表。
- 点击“应用候选”只更新当前页面的候选；发布前再次校验变更差异、权限、平台硬约束及模拟报告，阻止过期基准配置覆盖新值。
- 发布事务更新现有 `game_config` 当前行，并在同一事务写不可变审计。Admin 操作写 `admin_audit_event`，代理操作写 `agent_audit_event`；审计快照保存完整前后配置值、scope、模型/schema 版本和必要报告摘要，不保存逐轮样本或模拟结果账本。
- 生效只影响新建的游戏局/新投注；已开始牌局/投注继续使用开始时锁定的配置版本。
- 发布前的验收门槛可配置：目标范围通过、理论/模拟一致性、所有硬约束通过、重大变化二次审核。概率分布无法校验或数学模型版本缺失时禁止发布。

## 6. 后台页面设计

路径建议：`运营后台 → 游戏配置 → 选择游戏/难度 → 期望计算器`。

页面分为四块：

1. **配置上下文**：游戏、难度、草稿/已发布版本、规则版本、模型版本、活动 profile 状态。
2. **目标与约束**：显示适用于本游戏的指标，不呈现无意义通用字段；选择优化目标、参数白名单及范围。
3. **结果对比**：当前配置与候选配置并排；表格给出理论/模拟值、区间、样本、风险提示；提供概率分布/奖级分解和结果序列直方图。
4. **变更审阅**：机器可读差异、配置约束检查、说明理由、申请发布。1000 轮快速模拟用清晰标签，不能用“最终赢率”作为含混标题。

页面的所有数字由服务端报告 DTO 生成，前端只格式化展示。管理员只能看到其权限范围内的游戏与难度配置。

## 7. 系统架构和项目落点

建议 monorepo 模块：

```text
apps/admin-web/                         # Vue 管理端计算器 UI
apps/api/src/admin/game-math/           # 权限、schema、任务 API
apps/workers/math-simulation/           # 无钱包/DB 写权限的短任务 worker
packages/game-math-contracts/           # 请求、报告、指标枚举
games/<game_key>/math/                  # 游戏自己的精算、模拟与优化边界
```

1000 轮应在后台 worker/受控 Worker Pool 中跑，避免阻塞 HTTP 与实时 Socket.IO 事件循环。Web Worker 只解决计算隔离和 UI 响应，不代表“网络空闲下载 worker”。初版可用 Node worker_threads 或受限任务进程；每个任务有并发/CPU/超时上限，不需另行引入重型数学平台。任务只返回报告，不写游戏表。管理端若直接试算纯前端预览，也必须将后端重复校验作为发布权威。

生产配置的编辑/发布经 Admin 或 Agent HTTP API，并分别执行独立 capability；游戏服务只消费经过 schema 校验并已发布的配置快照。长模拟使用带 TTL 的 Redis task state 提供进度/取消/短期结果领取，Socket.IO 只推送进度和完成提醒，断线后可经 HTTP 查询尚存任务状态；Redis task key 过期不影响已发布配置/审计，也不产生业务结果丢失。正式配置与发布审计仍由 MySQL 事务负责，不能依赖 adapter 有限长度 stream 或 Redis 临时任务状态。[Socket.IO Redis Streams Adapter](https://socket.io/docs/v4/redis-streams-adapter/)

## 8. 每类游戏最小数学报告

| 游戏模型 | 快速模拟单位 | 必报核心结果 | 额外场景 |
| --- | --- | --- | --- |
| 跳高高（`slot5`）/ 夺宝奇侠（`slot3`） | 一次完整转轴及免费局链 | 按各自多线+积分规则模拟实际 RTP、轮空率、大奖率、返还/净值分布、方差 | 奖级贡献、连锁深度、最大派奖 |
| 麻将胡了/2、赏金女王 | 一次完整玩法周期 | 模拟实际 RTP、轮空率、大奖率、分布、方差 | 特殊模式、免费局、奖池状态 |
| 捕鱼 | 固定时长或固定发炮 scenario | 每炮/会话实际 RTP、轮空/命中率、大奖率、收益分布、方差 | 鱼群状态、目标竞争、武器档位 |
| 十三张 | 一整桌发牌/结算 | 桌级胜率、轮空/零分率（按规则定义）、大奖事件率（如适用）、净分分布与方差、打枪率 | 对手策略、机器人比例、档位规则 |
| 3快 | 一次完整期次/投注类型 | 理论/模拟命中率、空奖率、大奖率、返还分布与方差 | 官方号码空间、数据源样本不改概率 |

表中每项是游戏 handler/math module 的责任。暂未实现完整规则的外部游戏只显示“模型未就绪”，不能生成伪精确报告。

## 9. 验收标准

1. 运行 1000 轮后，MySQL 中无新增 game round、order、asset operation/entry 或钱包余额变化；Redis 只可有有时效的任务协调数据。
2. 模拟 worker 无 DB 写入凭证、无生产钱包依赖、无真实支付/开奖调用；固定 seed 与版本产生可复现结果。
3. 配置 schema 越界、未知 key、概率权重和不为正、奖项金额非法时拒绝运行或发布。
4. 对可枚举模型，精确结果和模拟区间能按容差对照；小概率奖项在 1000 样本时明确警告。
5. 优化结果只生成候选，不直接更改 published config；发布有完整操作者/审核者/前后值审计。
6. 配置更新不改变已开始牌局/投注的锁定版本。
7. 管理端分别显示“理论值”“模拟估计”“置信区间”“样本数”，不只显示单一赢率。
8. 权限、运行超时、资源上限、取消任务、重复提交与 worker 崩溃场景通过测试。

## 10. 当前浏览器实现状态

当前离线开发切片只登记了十三张 `classic_v1` 数学模型：`games/shisanshui/rules/src/simulation.ts` 对 52 张牌洗牌、给四个席位各发 13 张，再以 `rank_sorted_partition_v1` 将各手牌按点数拆墩，并调用规则模块的 `settleRound`。结果显示净水分布、策略胜/平/零净分率、相公率、打枪率、全垒打率、净分均值/方差/标准差，以及各比例的 Wilson 95% 区间和均值区间。固定 seed 可复现；计算只在浏览器内存运行并逐批交还渲染，不写入 IndexedDB、MySQL 或 Redis。

该拆墩策略只是让页面和共享报告契约可以端到端运行的分析样本，不是推荐机器人、最优策略或真实玩家分布。因此报告不得用于生产 RTP、玩家收益预测或概率发布。十三张的 RTP 显示“不适用”。页面里的计分配置仅为 `LOCAL_CANDIDATE`：前端执行本地范围校验并供试算读取，离开页面即丢弃；后端配置版本、审计事务、任务队列/取消、权限、优化器和正式发布尚未实现。除十三张外的游戏没有登记模型时返回 `MODEL_NOT_READY`，不得用通用假数据补位。

桌面浏览器已验收十三张配置和结果页及 Slot 模型未就绪页，视口为 1200×2029；记录值均为 `document.documentElement.scrollWidth/clientWidth = 1200/1200`、`scrollHeight/clientHeight = 2029/2029`。当前浏览器工具无法切换 Mobile viewport，因此移动端几何仍未验证。

## 11. 参考资料

- [NIST/SEMATECH e-Handbook：Confidence Interval Approach](https://www.itl.nist.gov/div898/handbook/prc/section2/prc221.htm)——统计区间的基础参考；具体 Monte Carlo 区间需由模型按数据分布选用合适方法。
- [Socket.IO Redis Streams Adapter](https://socket.io/docs/v4/redis-streams-adapter/)——适合官方 Socket.IO 多节点转发并支持短时连接恢复；有限保留不等于业务消息持久化。
- [Socket.IO Delivery Guarantees](https://socket.io/docs/v4/delivery-guarantees/)——默认服务端事件不保证断线期间补投；业务层需持久化、事件 ID 和断线游标补拉。
- [英国 Gambling Commission RTS 3](https://www.gamblingcommission.gov.uk/standards/remote-gambling-and-software-technical-standards/rts-3-rules-game-descriptions-and-the-likelihood-of-winning) 与 [RTS 7](https://www.gamblingcommission.gov.uk/manual/remote-gambling-and-software-technical-standards/rts-7-generation-of-random-outcomes)——作为概率说明与随机结果公平性的公开技术参考，不替代目标经营地区的合规判断。
