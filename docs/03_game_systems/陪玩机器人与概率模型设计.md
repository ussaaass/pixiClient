# 陪玩机器人与概率模型设计

阶段：平台级设计基线。覆盖十三张等棋牌陪玩，以及跳高高（稳定 ID `slot5`）、夺宝奇侠（稳定 ID `slot3`）、麻将胡了系列、赏金女王、捕鱼和定时开奖游戏的概率、结果展示与统计口径。跳高高为五列、夺宝奇侠为三列 Slot，多线+积分；本文不预设任何游戏的具体返奖率、奖表或第三方开奖结果供应商。

## 1. 原则：体验节奏与游戏结果分离

“起伏编排”若指动画、音效、镜头和揭晓节奏，只能用于**结果已由权威规则确定之后的展示**，不能影响该次结果。用户另行确认的“厅级双加成”是一个独立、公开、版本化的活动规则，可能改变活动期间概率和派奖，具体边界见第 5 节；不能把它伪装成单纯视听编排或隐藏在普通赔率中。服务器先按投注锁定的活动状态确定结果，客户端再呈现。

允许的体验编排：

- 按真实结果做清晰的揭晓节奏、牌桌镜头、音效层次和动画时长；弱网或用户关闭动画时可缩短/跳过，最终结果始终即时可查。
- 非现金的任务/收藏/成就进度按已公开规则推进；不得将任务文案包装成“下一局更容易赢”或暗示连玩可追回损失。
- 由玩家主动选择练习难度，或选择公开标记的机器人策略等级；这只能改变练习对手策略，不能改变发牌、开奖、中奖概率或正式房间的资产结算规则。
- 允许随机音乐/背景装饰变化和牌局叙事呈现，但“差一点中奖”的展示必须忠实反映真实结果，不能替换或伪造中奖线、差一符号、近失结果。

禁止将玩家近期输赢、充值额、余额、提现行为、停留时长、设备/IP/代理关系或行为画像输入 RNG、抽牌、开奖结果、鱼命中率、机器人出牌策略或派奖决策。禁止输后补偿、赢后压奖、按用户定制的概率和未披露的近失操纵。用户提出的“同厅爆奖后，全厅概率与奖额同时加成”是明确的产品活动规则：若允许概率变化，必须公开、全厅一致、仅由已公布奖池状态机驱动，且下注前展示实际概率/RTP；不能按个人定制。它是否可用于真实可兑资产，需要按运营地区/产品类别单独审查；未批准前可实现透明的奖池额外派奖而保持基础概率不变。每笔投注/round 开始时锁定活动状态和版本，不能中途改动。

原因很直接：若概率随着玩家行为改变，页面展示的赔率/返奖率就不再描述真实规则；“起伏”会从视听包装变成后台操纵。作为外部参考，英国 Gambling Commission 的 RTS 3 要求游戏说明规则、赢家判定与适用概率信息；RTS 7 明确反对补偿式自适应随机结果，并要求开奖结果符合理论概率。[RTS 3](https://www.gamblingcommission.gov.uk/standards/remote-gambling-and-software-technical-standards/rts-3-rules-game-descriptions-and-the-likelihood-of-winning) [RTS 7](https://www.gamblingcommission.gov.uk/manual/remote-gambling-and-software-technical-standards/rts-7-generation-of-random-outcomes)。这些是特定司法辖区的技术标准参考，不替代目标运营地区的法律审查。

## 2. 陪玩机器人设计

### 2.1 机器人身份与使用范围

- 机器人是房间中的 `seat_actor_type=BOT`，由 bot profile/策略版本驱动；它不是可登录玩家，不伪造真人的头像、在线状态、聊天身份或战绩。
- UI 始终标识“AI 陪玩/机器人”，匹配前说明本桌有机器人；战绩和统计把真人与机器人分开。
- 首版建议只在免费练习房、明确标注的练习档或不涉及可兑资产的场景开放机器人补位。真人现金/可兑金币桌若要机器人入座，必须经过独立产品与地区合规评审，明确展示其身份、资金对手方和结算方式，不得静默混入。
- 机器人可在真人等待超过配置阈值后补位；有足够真人时优先真人匹配。提供退出/等待真人选项；机器人数量、补位策略和平均等待时间不虚报。
- 机器人账号不复用真人 `user` 凭证。若资金结算要求机器人有经济对手方，使用显式的系统游戏账户/专用结算主体及独立流水标记，绝不在普通真人 user 身份下伪装；由 system account 风险上限控制暴露。
- 真人玩家超时后的单次动作托管不是“机器人陪玩”：不占新座位、不作为对手、不计入机器人入座/胜率指标。它由当前游戏 handler 在该玩家的操作截止后生成一个合法动作，来源标记为 `timeout_bot`；下一次操作窗口仍由玩家开始，若再次超时才再次代行。整局未结束时玩家重连恢复原座位和权威状态，已经受理的托管动作不撤销。

### 2.2 信息边界与决策

机器人策略只可读取与该座位真人相同的信息：自己的手牌、规则配置、公开桌面状态、已发生的公开事件和服务器时间。不得读取其他玩家私牌、未揭示的开奖结果、RNG 种子/后续结果、钱包/充值/代理画像或运营后台数据。

十三张策略封装在 `games/shisanshui/server/bot/`，复用正式规则 evaluator 校验摆牌：

- 策略档位通过明确配置定义目标（如优先合法、均衡、进阶），不针对特定真人或资产状态定制。
- 随机变体由服务端安全随机源生成；记录 `botProfileVersion`、难度、决策时间和输入快照摘要，足以复核策略版本，不公开他人隐私。
- 自动摆牌不能绕开倒道/牌型合法性校验。决定时间分布应自然但有上限，并由房间截止时间约束；延迟只做表现，不用于针对玩家拖延或抢时。
- 禁止机器人同伙协作、泄漏牌情报、串通输赢或故意打某一真人；多机器人座位之间不得共享未公开游戏状态。

游戏 SDK/后端以平台提供的 `BotSeatPort` 注入机器人动作。机器人不拥有原始 Socket、钱包仓储或任意 DB 访问权限；所有动作与真人命令经过同一 handler、顺序控制、规则校验和事件审计。

### 2.3 可观测指标

按游戏/房间档/机器人策略版本分别观察：机器人入座率、每桌机器人数量、真人等待时间、超时率、合法动作率、各策略胜率/平均分、对真人和其他机器人的结果分布。练习房数据单独标记，不与真钱/可兑资产对局混算；机器人指标不得被用来秘密调整随机结果。

## 3. 概率与“赢率”口径

不存在一个可用于所有游戏的“总赔率/总赢率公式”。游戏目录需按玩法展示适当指标，指标和规则配置同版本锁定。

### 3.1 单人随机派奖游戏：Slot、转轴类麻将主题

对一次下注额 `B`，对每个可能结果 `i` 定义概率 `p_i` 和**含退回本金在内**的总返还 `G_i`：

```text
理论 RTP             = Σ(p_i × G_i) / B
玩家单次净期望         = Σ[p_i × (G_i - B)]
理论 house edge       = 1 - RTP
命中率（需定义“命中”） = Σ(p_i)，只对满足产品公布的命中条件的结果求和
盈利率                = P(G_i > B)
```

必须区分“有任意派奖的命中率”`P(G_i > 0)`、“收回本金”`P(G_i ≥ B)`和“本局净盈利率”`P(G_i > B)`；它们不是同一个数。免费旋转/奖励局需要将整条状态链计入预期返还，不能只用基础转轴命中率代替总 RTP。多阶段规则可用完整枚举、马尔可夫吸收链或可复现 Monte Carlo 独立交叉验证。

转轴独立时，某组合 `s_1…s_n` 的概率为 `Π_j P_j(s_j)`；若每轴按权重 `w_{j,s}` 选择，则 `P_j(s)=w_{j,s}/Σ_s w_{j,s}`。中奖线/ways/散布奖、Wild/Scatter、免费局等按该游戏正式判奖代码枚举，不靠人工估一个“理论赢率”。每个实际标题（跳高高、夺宝奇侠、麻将胡了、麻将胡了2、赏金女王）是独立配置和测试单元，不能只因玩法相似就共用未验证的数学模型。

### 3.2 捕鱼：连续成本/奖励模型

对某次发射成本 `C`，令服务器认可的目标类型为 `j`，击中/捕获概率为 `p_j`，对应含本金口径一致的总返还为 `G_j`：

```text
单发期望净值 = Σ_j(p_j × G_j) - C
单发返还率   = Σ_j(p_j × G_j) / C
```

若发射会影响鱼群状态、多个玩家竞争同一目标、炮弹飞行时间/武器等级改变成功率，就必须按完整场景状态建立概率模型或仿真；不能把静态“鱼倍率”误称为实际捕获率。服务器目标与捕获裁决是权威结果，客户端弹道仅负责展示。

### 3.3 外部数据源定时开奖（暂称“3快”）

每个投注类型按数据源开奖空间计算 `p_i`，派奖规则得出 `G_i`，仍使用前述 RTP/净期望公式。若奖金池依赖当期期数/投注总额，应说明分配公式与封顶/舍入规则；在开奖之前固化投注快照和规则版本。概率须基于可验证的开奖结果空间，数据源响应、期号、校验结果及最终结算关联留审计记录。

### 3.4 对战类：十三张等玩家互相结算

对战游戏没有固定 RTP。给定规则版本 `r`、玩家策略 `s`、对手策略/人群分布 `D`，定义：

```text
胜率           = P(本方最终积分 > 对手最终积分 | r, s, D)
平局率         = P(积分相等 | r, s, D)
每局期望净分   = E[本方净结算分 | r, s, D]
每局期望资产变化 = E[本方实际金币变化 | r, s, D]
```

四人桌需明确“胜过任一对手”“三家全胜”和“最终净分为正”的不同口径。打枪、全垒打和特殊墩计分全部进入模拟/精确计算。真人对真人时，桌面总分按规则通常守恒或由规则定义；平台手续费/服务费单独作为平台收入，不伪称 house edge。陪玩机器人的加入会改变对手分布 `D`，所以真人胜率必须按无机器人/机器人档位分别披露或至少明确分组统计。

### 3.5 统一平台收入

平台收入不等于“玩家输的钱”。按玩法分别记录：

```text
平台净收入 = 玩家支付的平台明确费用
           + 游戏产品（若有）理论毛利
           - 渠道成本、优惠补贴、返佣与奖励成本
```

玩家间结算、系统账户承担的机器人对手结果、充值赠币、代理奖励和支付渠道成本分别记账。不得用机器人输赢或不透明补贴掩盖实际游戏 RTP/费用。

## 4. 赔率与概率的配置/发布

每个游戏模块实现自己的 `GameMathModel`（概率、派奖、版本校验器）和独立结果模拟器；平台只提供统一录入、审核、发布和报表接口：

```ts
interface GameMathReport {
  gameKey: string;
  mathModelVersion: string;
  configVersion: string;
  theoreticalRtp?: string;       // 精确十进制或有理数，禁止浮点作为账本值
  hitRate?: string;
  netWinRate?: string;
  houseEdge?: string;
  simulationRuns?: string;
  confidenceInterval?: { lower: string; upper: string };
  botProfileVersion?: string;
  generatedAt: string;
}
```

要求：

- 高概率/简单模型优先精确枚举或有理数计算；Monte Carlo 用于复杂模型验证，固定算法/配置/样本量并给出置信区间。不能把有限样本跑出的 RTP 当作精确数学值。
- 开放新赔率/玩法配置前，生成数学报告与自动化对照测试；报告与代码 commit、模块版本和已发布 `game_config` 版本关联。
- 运行后按版本做实际 wager、payout、RTP/胜率、偏差和置信范围监控；监控触发审计/暂停调查，不通过动态调概率“修正”偏差。
- 概率、返奖规则、服务费、机器人是否在桌等可理解信息应在玩家操作前展示。不得用总体平均掩盖显著不同的档位/玩法配置。
- 金额账务使用定点整数的最小单位；赔率/概率计算用整数权重或精确有理数，规定奖金舍入方向并在规则中披露。
- RNG/开奖处理和钱包结算彼此独立测试；实际账本按用户确认的双资产与流水规则执行。

## 5. 厅级共享活动：资金、概率与营销边界

厅级活动将由通用事件系统提供：触发事件类型和阈值由游戏子厅配置决定；广播可显示经过脱敏的事件主体，且该主体本人不接收这条全局公告。15/50 席位现按可配置的真实容量处理，不假设有固定虚假席位。

事件引擎不内置某一种触发条件。每种 trigger 要在 `game_config` 注册 schema 和公开/私有策略；若属于可公开事件，可以只向其他玩家发送脱敏公告，并在 feed/API 层排除事件主体。真实席位容量必须准确显示、由服务端执行。若活动改变游戏概率，仍须独立验证概率分布和 RTP；完整事件、公告和主体过滤链路见[平台事件与广播系统设计](./平台事件与广播系统设计.md)。英国 Gambling Commission 的 RTS 7 将补偿式自适应游戏列为随机结果公平性问题，RTS 3 要求准确说明规则和中奖可能性。[RTS 7](https://www.gamblingcommission.gov.uk/manual/remote-gambling-and-software-technical-standards/rts-7-generation-of-random-outcomes) [RTS 3](https://www.gamblingcommission.gov.uk/standards/remote-gambling-and-software-technical-standards/rts-3-rules-game-descriptions-and-the-likelihood-of-winning)。这是英国标准的参考，目标地区上线前仍需独立审查。

可保留的产品目标是：**全厅真实活动播报 + 明确资金来源的共享奖励池**。播报可以由实际、可审计的活动事件触发；概率保持基础配置不变，奖励池只支付明确的额外奖励；展示真实池余额、有效时间与适用范围。不使用假名额、假机器人战绩、输光用户的身份/损失金额或“赶快来赢”的催促文案。

### 5.1 生效范围与状态

- 唯一作用域建议为 `gameKey + difficultyKey + gameConfigVersion`。同厅真人看到同一活动状态和规则；不同难度/游戏不共享，除非 Admin 显式配置。
- 席位只有在作为真实活动容量限制时才保留：服务端对 `eventId + userId` 原子占位，同一账号跨设备只占一席；进入对应厅自动占位（沿用用户此前确认）；真实满席后如实显示已满。不得将实际无容量限制的活动包装成 15/50 席。
- 退出、切厅和断线释放策略由服务端统一处理。建议离厅释放，短暂断线进入配置的恢复宽限期；同一玩家在名额释放后可以按真实剩余容量重新进入。占位不等于下注，不自动扣款。
- 该活动应从同一份服务端 `PromotionEvent` 状态，经平台 HTTP 初始快照和平台 Socket.IO 更新，投递到游戏大厅跑马灯、对应游戏子厅横幅和游戏内 HUD。页面只呈现同一个 `eventId/stateVersion`，不能各自推算倒计时/剩余名额。
- 若产品保留活动时长，15 分钟或真实奖池耗尽先到者结束；不同目标游戏/难度的资金池和状态分别展示。跑马灯可关闭/静音，查看活动不自动下注。
- 游戏专属 server handler 只在服务器确认合格大额结果后发出 `QualifiedMilestone`；客户端不能自行触发。机器人事件不能触发活动，也不能获得活动奖励。
- Boost 状态在新投注/新 round 接受之前原子切换。每笔投注锁定 `boostEventId、boostConfigVersion、oddsProfileVersion、poolStateVersion`；已受理投注/已开始的 round 保持原状态。
- 状态至少包括 `inactive → active → draining → exhausted`。`draining` 表示共享奖池可用余额已被待结算奖励预留占满，停止接受新的加成投注；已锁定的结算继续处理。只有真实可用余额为零且无未决预留，才转为 `exhausted`。
- 池余额或赔率状态不能只存在 Redis。Redis 可作实时协调缓存；奖池资金增减、活动触发、版本状态、投注预留与派奖结果必须能通过不可变资产流水/审计记录恢复与核对。

### 5.2 双加成数学模型

设基础投注额为 `B`，基础结果 `i` 的概率为 `p_i`，基础含本金总返还为 `G_i`。活动状态 `z` 下：

```text
活动结果概率：p_i(z)，Σ_i p_i(z) = 1
活动总返还：  T_i(z) = G_i × payoutMultiplier(z) + poolBonus_i(z)
活动 RTP：    RTP(z) = Σ_i[p_i(z) × T_i(z)] / B
活动净期望：  EV(z) = Σ_i[p_i(z) × (T_i(z) - B)]
```

`p_i(z)` 必须由已发布的 odds profile 明确给出，不能用“概率 +20%”这种未说明归一化方式的模糊参数。可用的数学配置形式是对互斥结果组配置整数权重 `w_i(z)`，然后 `p_i(z)=w_i(z)/Σ_j w_j(z)`；同时发布结果组概率、命中率、净盈利率与 RTP。若只给某类中奖结果乘权，归一化会降低其他结果概率，必须一起披露。

`poolBonus_i(z)` 和额外派奖倍数由该有限奖池承担，必须受可用余额限制。有效 RTP 报告至少分别给出基础状态与加成状态；厅活动期间用户展示加成状态下的 odds/RTP 和奖池规则。奖池加成贡献不可隐藏在基础 RTP 中。

由于中奖会消耗奖池、合格爆奖会改变活动状态，整场活动不是独立同分布的重复下注。除每个已锁定状态 `z` 的条件 RTP 外，还要计算从启动到耗尽的**活动周期累计返还**：`campaignRTP = E[Σ settled gross returns] / E[Σ accepted stakes]`。状态至少包含剩余奖池/预留、当前 odds profile、派奖倍数和事件版本；用马尔可夫奖励过程精算或按真实状态转移做 Monte Carlo，报告活动持续期和置信区间。不能只用某个“加成中的 RTP”代替整个奖池生命周期的期望。

### 5.3 并发、耗尽与奖池资金

在接受投注之前，原子检查活动状态并预留加成的最大/可承诺敞口；结算按 `betId/roundId + boostEventId` 幂等。多节点不能各自用本地缓存判断余额；用数据库条件更新/事务或单一受控 actor 序列化可用池余额与 reserve。超时和重试不得二次预留/派彩。

建议奖池只承担“高于基础派奖的那部分”；基础结果派奖仍由游戏既定结算模型处理。奖池用独立 system asset account/operation 标识来源与去向，设置每厅池上限、每注加成上限、最大同时未决敞口和运营预算。不能通过透支玩家余额兑现促销，也不能把普通资产账目与促销负债混成一个未区分的值。

若奖池资金来自玩家下注/净输，应当在该类游戏的公开规则中明确其计算基数与比例，并在账本中表现为实际费用/分配，不得把玩家支付给其他玩家的对战输分暗中当作平台资金。十三张等 P2P 游戏的输分通常结算给赢家；抽取 15% 就改变了原有结算并构成额外费用，必须单独定规则。Slot/捕鱼等系统对手玩法也要定义是从游戏毛收入、净收入还是独立营销预算注资。机器人没有真实玩家资金损失，不能将机器人虚拟亏损计入用户损失池或包装成真人触发。

“直到奖池清空”必须定义清空口径：建议 `availablePool = fundedPool - settledBonus - outstandingReservedBonus`；`availablePool=0` 后停止新加成投注。对已受理投注，按其锁定的 odds/payout profile 完成结算；若预留设计不能覆盖最大承诺，不得继续接受该下注。池充值/补充会生成新的 `boostEventId` 或 pool epoch，不能无提示复活已结束活动。

### 5.4 不适用范围与待定

- **十三张/PvP 扑克类**：不能因某人输光而改洗牌、发牌概率或对真人的配桌概率。可对相同厅提供透明额外奖励；若将输分抽 15% 入池，则必须先定义公开平台费用及赢家净得，不能沿用原先“赢家收取输分”的计分口径。
- **3快/外部数据开奖**：开奖号码由外部数据源确定，系统不能提高某一号码出现概率。可以按事先展示的 pool bonus 对命中订单额外派奖，但开奖概率不变。
- **Slot/本平台控制结果的游戏**：不要按某位玩家输光或奖池余额变化做动态概率补偿/惩罚。若未来考虑活动赔率，必须先有明确、公开、获准的完整赔率配置和按状态审计；生产首版建议保持基础概率不变，只由独立、有预算的促销池额外派奖。
- **捕鱼**：命中概率若改变，必须公开鱼种/炮倍/命中率与活动 RTP；同厅共用的奖励池也可提高捕获奖励。活动不能读取单个玩家输赢历史。

仍需产品配置明确“爆奖”阈值、奖池注资来源、奖池显示方式、odds profile 的具体权重/倍率、派奖倍率、每注/每厅上限、池耗尽后待结算注单规则，以及同一时刻多次触发如何延长/刷新。没有这些配置和数学报告，不能给具体概率数字或投入生产。

### 5.5 大厅、子厅与游戏内同步展示

同一条真实 `PromotionEvent` 可以同步到大厅跑马灯、子厅横幅和游戏内 HUD。播报不展示用户“输光”、连败次数、损失额等敏感行为，也不把机器人包装成真人。15/50 或其他席位上限只有在后台真实配置、服务端实际限制时才可展示；不能以虚假席位/剩余人数刺激入场。

建议的中性播报模板：

```text
《{游戏}·{难度}》共享活动已开启。
活动资金池：{当前可用奖池}；有效至 {结束时间} 或奖池耗尽。
适用范围：{目标游戏与难度}；真实参与席位 {已占用}/{实际上限}。
活动概率/派奖变化：{本游戏已验证并获准展示的明细}。活动规则：[查看详情]
```

广播规则由已登记的 event type 决定；如公告主体是玩家，向其他受众显示脱敏身份，并把主体排除在该公告的推送与补拉结果之外。触发条件和文案都由服务端审核配置决定，不在平台引擎中写死某个特定行为。

如果未来有经过审核的活动赔率，应显示该游戏真实的基础/活动概率与派奖差异；十三张和外部开奖型游戏只显示额外奖池奖励，不能声称中奖概率提高。奖励活动可说明“15% 的公开注资比例”，但要说明基数是何种已结算收入，不把玩家净输金额作为系统当然拥有的资金。

所有页面使用同一服务端状态：HTTP 提供初始快照，平台 Socket.IO 推送状态变化；客户端不自行计算余额、事件终止或赔率。大厅显示摘要并可关闭跑马灯；子厅显示适用范围、实际池余额和规则；游戏内 HUD 显示本次玩法有效配置和活动剩余时长。用场景灯光、音效和视觉庆祝营造线下厅氛围，但不使用“快来抢”“下一位就能中”等催促或暗示性文案。

## 6. 模块边界与测试

新增共享端口 `BotSeatPort` 与 `GameMathModel` 仅是宿主协议，不把十三张策略或 Slot 概率写进平台包。推荐目录：

```text
games/<gameKey>/
  bot/                 可选；只服务该玩法的策略
  math/                概率、派奖、模拟器与数学报告
  promotions/          可选；游戏专属高光事件判定，不直接发放资产
  server/              权威 handler；调用 math/rules
  client/              只展示快照/事件，不能决定结果
  tests/                规则、概率、机器人信息边界与结算契约
```

最低验收：

1. 每个可派奖输出的概率非负，总和在精确计算下为 1；加权结果分布与数学模型一致。
2. Slot 各中奖类别、奖金和免费局贡献与奖表逐项对照；理论 RTP 与独立枚举/仿真在设定容差内。
3. 定时开奖使用外部公开结果时，映射与投注结算用历史样本回放，期号重复、迟到、格式错误和更正都有确定处理。
4. 十三张使用发牌枚举/抽样验证牌张互斥、合法摆牌与计分；机器人和真人调用同一规则 handler，机器人不能读取私有状态之外的数据。
5. 捕鱼压力/仿真覆盖不同鱼群状态、武器参数和多玩家竞争；高频视觉事件压缩/合批不得丢失资产相关结果。
6. 大厅、规则页和牌桌显示的版本/规则与服务器快照完全一致；改配置不能影响正在运行的 session/round。
7. “起伏编排”相关验收只改展示层：替换动画/音效策略前后，对相同服务器结果的概率、奖金、积分和账本事件逐字节/逐字段一致。
8. 厅级加成并发 trigger、边界时间下注、缓存重建、重复事件和预算耗尽测试通过；真人可见的活动快照与最终奖励逐项匹配，bot 不能触发或领取真人促销奖励。

## 7. 待确认但不阻塞总体设计

- 陪玩机器人首版只建议进入免费/练习场；是否允许在可兑金币房出现机器人、其身份展示与系统账户对手敞口，需要单独产品决议。
- 用户确认席位可以是真实容量：15/50 可作为配置值候选，进入对应厅自动占位，必须由服务端真实限额。事件 trigger 由各子厅注册并配置；若事件带玩家主体，按公告策略脱敏且本人不接收该条。若启用 odds profile，需逐玩法定义结果概率并计算 RTP，经地区审查；十三张/3快不因活动改发牌或外部开奖号码。
- “3快”所用开奖数据源、期号、漏期/延迟/更正策略与封盘权威时钟，在该模块开发前确定。
- 各 Slot/捕鱼具体 math model、正式赔率/奖表、返奖率及展示口径由游戏产品配置与独立数学审核逐款确定；没有这些输入时不能填造具体 RTP 数字。
