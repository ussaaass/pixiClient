# PC 大厅游戏卡片与动效背景 SDD

版本：0.4（PC 9:16 专用卡片背景与焦点循环动效）  
日期：2026-10-11  
范围：PC 大厅全视口横向游戏卡带中的 9:16 竖向卡片、各游戏专属 AVIF 背景、中央 C 位动效及兼容/加载策略。手机大厅仍按[玩家大厅 Mobile 布局与视觉 SDD](./玩家大厅Mobile布局与视觉SDD.md)显示十三张首卡和移动布局。

## 1. 目标与边界

桌面游戏目录使用 9:16 竖向卡片组成横向滚动卡带，卡带的可视滚动区延伸至浏览器 viewport 全宽。每款游戏拥有自己的 AI 创作背景；卡片成为卡带中央 C 位并停止滑动后，才加载并播放该游戏的循环 AVIF 动效。其他卡片显示该游戏的静态背景，既让整排有各自主题，又不同时解码多段动画。

桌面大厅主容器高度固定为动态视口高度，游戏卡带弹性占用其余空间，卡片按卡带实际高度维持 9:16；横向溢出由卡带自身滚动承载，不得把大厅页面撑出纵向滚动条。大厅和子厅面向玩家的界面不展示“预览”“待接入”等施工状态控件；无法使用的功能不伪装成可操作入口。

本 SDD 记录视觉与交互方案，并登记八款游戏图标和卡片背景的 AI 图像成果。桌面卡片使用本轮重新生成的 9:16 竖图作为全卡背景；Mobile 线上仍使用原来的宽幅背景，不受桌面素材替换影响。2026-10-18 已新增两组独立 Mobile 竖版静态候选，分别位于 `assets/candidates/mobile-game-cards-v1/` 和 `assets/candidates/mobile-game-cards-openai-v1/`，均未接入线上；用户选择以 OpenAI 第二组作为 Kling 动效输入，但不代表已批准发布，赏金女王沿用当前素材。Kling v3 已生成第一批七款及第二批五款纠错动效，均派生为 537×960、40 帧、8 fps 无限循环 AVIF；素材、提示词、模型和请求 ID 记录在候选目录及 job 台账。抽帧复核发现第一批麻将胡了 2 使用空白麻将牌、捕鱼题材错误、3快无号码，十三张会重绘牌面且跳高高未显著转动；第二批修正了捕鱼母图并通过题材和位移抽检，但十三张、3快及跳高高仍未通过视觉验收。所有候选仍未接入线上。图标与背景都是独立资产：图标作为 PC/Mobile 的方形游戏识别图，背景不包含游戏名、按钮、赔率、开奖数字或品牌文字。十三张牌面遵循传统扑克牌视觉，不生成卡通 J/Q/K 角色。各游戏的视觉锚点、创作提示词和资源清单见[八款游戏图标与卡片背景重制说明](../07_assets/八款游戏图标与卡片背景重制说明.md)。

“C 位”是滚动轨道几何中心最近的一张卡。初次进入 PC 大厅时仍让第 4 张十三张居中；之后卡带每次停止滑动时更新 C 位。规划中游戏可展示专属背景与动效，但 CTA 明确显示“敬请期待”且不可进入。

## 2. 桌面卡片构图

- 卡片外框与 PC 专用背景均采用 9:16 竖向比例，宽度依据 viewport 高度响应。卡带铺满 viewport；首端仅按“第四张十三张居中”所需增加自适应间距，不足时为零，避免首张跳高高因可居中空白成为 C 位。首卡用 start 吸附；尾端保留足够滚动余量，使最后一张卡仍可滚入中心区。
- 9:16 AI 背景铺满整张卡片，`object-fit: cover` 按比例裁切，不拉伸；卡片下半部的渐层承载方形游戏图标、类别/开放状态、标题、简介和 CTA，信息超出时截断而不撑破卡片。移动端继续使用原有宽幅背景和既有移动排版。
- 卡片以中心吸附方式横向滚动，首卡在轨道起点靠左对齐，其余卡片按中心吸附。卡带隐藏可视滚动条，保留触控板/横向滚轮、聚焦后方向键和触摸滑动；页面本身不得因卡带产生横向滚动。
- 卡片表面叠加由透明至底部深色的渐层，保证图标和文字可读。所有文字及状态来自 H5/DTO，保证清晰、可翻译且不会随 AI 图片产生错字。
- C 位使用暖金边框、轻微亮度/景深提升和不超过 1.025 的缩放。缩放只做视觉层，不改变轨道测量与吸附位置。非中心卡保持静态、亮度略低但仍清晰可读。
- 动效只在滚动停止并选出 C 位后启动；滚动期间卸载/暂停上一张的动效，新的 C 位先显示海报，再异步载入动效。任何时刻最多一个卡片动效运行。

## 4. 动效素材规格与生成流程

每款 PC 背景交付一张 AI 生成的源图、静态 AVIF 海报、WebP 回退图和一段循环动态 AVIF。动态 AVIF 从对应母图经确定性帧处理派生：3 秒内完成最高约 7% 的镜头推近与往返横纵位移，最后一帧回到首帧位置；不改变转轮符号、麻将牌面或开奖结果。桌面焦点卡还叠加 CSS 镜头漂移，使浏览器只显示 AVIF 序列主图时仍有可见变化。CSS 动效只作用于桌面焦点卡，遵循 `prefers-reduced-motion`。这属于从静态图派生的镜头动画，不记作 AI 视频生成。

| 变体 | 规格建议 | 加载/使用 |
| --- | --- | --- |
| PC 源母版 | OpenAI 图像母版，原始 PNG 保存在 `assets/aigen/game-cards-v3-portrait/sources/{assetKey}.png`；941×1672，约 9:16 | 不进入客户端；用于桌面竖版重导出与动画制作 |
| PC 静态海报 | AVIF 540×960；同构图 WebP 回退 | 桌面卡片按需加载，背景铺满 9:16 卡片 |
| PC 中央动效 | 动态 AVIF 432×768、24 帧、8 fps、3 秒循环 | 从竖版母图确定性派生镜头推近与横纵位移；仅 C 位/悬停卡加载 |
| Mobile 背景 | 线上沿用既有宽幅 AVIF/WebP；新一批静态及 Kling AVIF 都处于审核候选目录 | 新版竖图只由 `(min-width: 721px)` source 选择 |

以上为接入文件实测体积，逐个检查了静态/动态格式、图标尺寸和 AVIF 帧数；仍需真机画质和跨浏览器验收。桌面八张静态 AVIF 合计约 864 KiB，单张为 80–140 KiB；八段动态 AVIF 合计约 2.3 MiB，单段为 196–420 KiB，不得一次性预取。首屏只请求当前焦点卡动效，其余动效保持未请求。图标共约 792 KiB；Mobile 仍使用上一批宽幅资源。

生成步骤：桌面首批 OpenAI 图像生成产出八张风格统一母版，再从同一母图用确定性帧处理制作镜头漂移循环；该批资源已接入桌面卡片。Mobile 新候选由 OpenAI 第二组 9:16 静态图作为 Kling v3 图生视频输入，经 5 秒标准模式生成 MP4，再以 ffmpeg/libaom-av1 编码为 537×960、8 fps、40 帧、CRF 30 的无限循环 AVIF。首批七款文件约 185–406 KiB；第二批五款约 205–529 KiB。两批 Mobile Kling 素材都只用于审核，未复制到正式前端资源目录，也未更换当前线上背景。逐帧复核时重点检查主体题材、游戏符号一致性、可读文字/牌面是否保持、动作幅度及首尾过渡；通过 AVIF 容器校验不等同于美术验收。

## 5. 中心卡选择、播放和加载状态

1. 卡带初始化按既有大厅顺序将第 4 张十三张滚到中心；静态海报先出现，不等待动画。
2. 从钱包、社区、消息或个人页返回大厅时，重新绑定新挂载的 `.game-row` 滚动监听并重新对齐 C 位；页面路由会销毁旧轨道节点，不能复用首次挂载时的监听器。
3. `scroll` 时将当前动画卸载，避免拖动期间同时解码多个 AVIF；用户停止滚动后，根据轨道中心与每张卡片中心的最近距离确定唯一 C 位。
4. 鼠标进入任意卡片时，该卡临时获得动效播放资格；鼠标移出后清除悬停态，并恢复当前 C 位动效。触屏指针不触发悬停态，避免触摸后动效卡住。
5. 每张卡的静态 poster `<picture>` 始终挂载并作为底图。获得动效资格时，另行挂载 active AVIF 覆盖层；在覆盖层图片触发 `load` 前保持透明，加载后淡入。焦点切换不得销毁或替换静态底图，避免新图请求/解码期间出现闪白或空图。
6. 如果动态效果允许且网络状态正常，只请求当前 C 位或悬停卡片的动效；其余卡片不请求 active AVIF。活动覆盖层离开焦点后卸载，静态海报持续可见。解码失败、请求失败或动效文件超限时显示静态海报，不出现空白卡。
7. 卡片离开焦点、文档进入后台、用户启用节省流量或系统偏好 `prefers-reduced-motion: reduce` 时停止/卸载动效并保留静态图；返回前台或关闭节流后，再根据当前焦点卡重新判断。
8. 中央高亮是卡片位置/焦点，不代表该游戏当前开放或中奖事件。禁用游戏照常显示动效和状态“敬请期待”；只有服务端目录状态决定 CTA 是否可用。
9. 图片加载失败时显示游戏专属纯色/渐层 CSS fallback、标题与详情仍可用；不因为美术下载失败隐藏卡片或阻止大厅操作。

建议资源键：`game-card-{gameKey}-poster-avif`、`game-card-{gameKey}-poster-webp`、`game-card-{gameKey}-active-avif`。游戏目录由 `Asset` ID 引用海报和动效，不硬编码 CDN 地址或把动态文件塞入 JS bundle。DTO 只给当前 capability 下可展示的 asset variant 引用；客户端资源调度器决定请求时机。

## 6. AVIF 兼容与退化策略

静态 AVIF 与动画 AVIF 的支持不能只根据扩展名推断。WebKit 曾发布 Safari 16.1 的动画 AVIF 支持及 16.4 的相关更新，但截至本 SDD 日期，WebKit 仍有 Safari 新版本动画 AVIF 空白渲染缺陷报告。故设计要求始终保留静态 WebP poster，并对 Safari、Chrome/Chromium、Firefox 的实际版本做验收；不能把动画 AVIF 作为唯一可见画面。`<picture>` 可提供图像格式/设备条件 fallback，但运行时动画是否成功还需资源错误路径与人工浏览器验收。[WebKit Safari 16.1](https://webkit.org/blog/13399/webkit-features-in-safari-16-1/)、[WebKit Safari 16.4](https://webkit.org/blog/13966/webkit-features-in-safari-16-4/)、[WebKit animated AVIF issue](https://bugs.webkit.org/show_bug.cgi?id=322274)、[MDN `<picture>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/picture)

静态 fallback 必须与 AVIF 海报构图一致；若动画能力不可用、首帧异常、动效下载失败或解码失败，用户仍看到完整静态主题图和 H5 文案。动画不是按钮状态、概率变化或派奖结果的唯一表达方式，也不得自动播音。

## 7. 共享资源与 DTO 约定

- 沿用 `GameCatalogDto` 和 `AssetDto/AssetVariantDto`；每款游戏在目录卡背景配置中关联 poster AVIF、poster WebP fallback、active-motion AVIF 三个 asset 引用。对未开放游戏，motion 引用可暂缺，不影响卡片内容。当前大厅卡片列表与 Admin 本机目录演练共同引用 contracts 中的 `LOBBY_GAME_REFERENCE`，用于保持离线开发显示一致；二者各自的 origin 隔离，Admin IndexedDB 编辑不会推送到玩家大厅，生产读取必须改由服务端目录 API 提供。
- 资源任务由大厅网络调度器管理：静态可见 poster 高于非可见 poster；首屏焦点确定后加载当前 C 位 active motion；网络转差或用户操作时暂停后台下载。切换 C 位不得影响 HTTP/Socket 游戏命令。
- 不另建 `GameCardBackground` 数据表；使用现有 Asset 实体和游戏目录配置关联，减少专用实体扩张。
- 卡片封面图标与背景职责分开：`/assets/game-icons/{assetKey}.webp` 在 PC/Mobile 复用；`/assets/game-cards/{assetKey}/portrait/` 提供 PC 9:16 背景，根目录保留 Mobile 宽幅背景。Mobile 十三张入口把图标放在标题行左侧，其他卡片沿用图标列+文本列；各图均按容器比例等比缩放，不把方形封面拉伸成宽图。

## 8. 闭环验收 Checklist

- ✅ PC 卡片与专用背景均为 9:16 竖版；背景铺满整卡，图标与文字/按钮分层；Mobile 继续使用旧宽幅背景。
- ✅ PC 卡带可视区域铺满 viewport；首端仅留第四张居中所需的自适应空间，首卡 start 吸附且不可成为初始 C 位，尾端保留滚动余量。
- ✅ 八款游戏各有一致风格下的独立主题/动效方向和 AI 提示词规格；Slot5/Slot3 的展示名称修订为“跳高高/夺宝奇侠”，稳定目录 ID 不变，两者均标记为 Slot 多线+积分。
- ✅ 首次进入时第 4 张十三张居中；运行时只有静止后的 C 位请求/播放动态 AVIF。
- ✅ 首版使用静态 AVIF、WebP 格式回退；C 位按中心卡切换动态 AVIF，鼠标悬停临时切换到悬停卡片，移出后恢复 C 位；触摸不锁定悬停状态。
